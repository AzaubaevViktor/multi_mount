# Прошивка DEC-контроллера: план правок

Плата: Arduino Nano ATmega328 (`platformio.ini` → `env:nanoatmega328`), **2 КБ SRAM**,
UART 115200. Файл: `telescope_dec/src/main.cpp`.

## Проблема

TX-кольцо `outBufV2[256]` (`main.cpp:151`) при переполнении **молча теряет данные**:

```c
static inline bool outAppendCharV2(char c) {
  uint8_t next = (uint8_t)(outWriteV2 + 1);
  if (next == outReadV2) return false;   // нет места
  ...
}

static inline void outAppendStrV2(const char* s) {
  while (*s) { if (!outAppendCharV2(*s++)) return; }   // молча обрывает на полуслове
}
```

Последствия по нарастанию тяжести:

1. Ответ обрывается посередине — хост читает мусор.
2. `outFlushLineV2()` (`:225`) — это тот же `outAppendCharV2('\n')`, он тоже может не
   влезть. Тогда ответ остаётся **без терминатора**, и следующий ответ приклеивается
   к обрубку: хост получает одну склеенную строку вместо двух.
3. Никакого сигнала о потере нет — ни флага, ни счётчика. Дефект невидим и в прошивке,
   и в логах хоста.

### Первопричина — скорость слива

```c
if (Serial.availableForWrite() > 0) {
  char c = 0;
  if (outPopV2(&c)) Serial.write((uint8_t)c);   // ровно 1 байт за итерацию loop()
}
```
(`main.cpp:1093-1096`)

Слив ограничен байтом за итерацию `loop()`. Ответ `status` — около 150 байт, то есть
~150 итераций на одну строку. Если хост опрашивает чаще, чем прошивка успевает слить,
кольцо копится и переполняется.

Ограничение выглядит как защита реального времени (в `loop()` крутится
`serviceStepperv2()`, задержка = потерянные шаги), но в этом виде оно избыточно:
у ATmega328 аппаратный TX-буфер 64 байта и передача идёт в прерывании, поэтому
`Serial.write()` **не блокирует**, пока `availableForWrite() > 0`. Слив пачкой в
пределах свободного места так же безопасен, как слив одного байта.

### Оценка риска по размеру ответа

- `status` (`:860-874`, 11 ключей) — ~150 байт, в кольцо влезает.
- `full_status` / `driver_status` (`:877+`) — 4 hex-ключа вида `key=0xXXXXXXXX;`
  (~20 байт каждый) + заголовок; отдельно короче, но идут следом за `status`.

Опасен не одиночный ответ, а **накопление**: два невыгребенных статуса (300 байт)
переполняют кольцо на 256.

Важно: увеличивать буфер — плохой путь. 256 байт это уже 12.5% всей SRAM платы.

## Что предлагаю сделать

### 1. Сливать пачкой, а не по байту (убирает первопричину)

В `loop()` писать столько байт, сколько свободно в аппаратном TX-буфере (с потолком
16–32 байта за итерацию, чтобы не растягивать шаговый цикл):

```c
uint8_t budget = Serial.availableForWrite();
if (budget > TX_DRAIN_MAX) budget = TX_DRAIN_MAX;
char c = 0;
while (budget-- && outPopV2(&c)) Serial.write((uint8_t)c);
```

Потолок `TX_DRAIN_MAX` подобрать замером: убедиться, что при полном сливе не растёт
джиттер шагов (аккумулятор шагов клампится на 8.0 в `serviceStepperv2`, так что
затянутая итерация — это потерянные шаги, а не отложенные).

### 2. Сделать ответ атомарным

Полуответ хуже честной ошибки: он молча портит следующий ответ. Перед формированием
проверять свободное место в кольце; не хватает — не писать частично, а отдать короткий
`0;error=tx_overflow;` (он гарантированно влезает, если резервировать под него место).

Реализация без переписывания всех `respond*`: завести флаг «текущая строка не влезла»,
который взводится в `outAppendCharV2` при отказе; в `respondEndV2()` при взведённом
флаге откатить запись строки (вернуть `outWriteV2` к позиции начала строки) и записать
вместо неё `0;error=tx_overflow;\n`. Для этого запоминать `outWriteV2` в
`respondStartV2()`.

### 3. Перестать молчать

Счётчик переполнений (`uint16_t`, с насыщением) + ключ `tx_overflow=N` в ответе
`status`. Тогда дефект виден в обычных логах хоста и попадает в статистику, а не
проявляется загадочным битым ответом раз в месяц.

### 4. На стороне хоста — различать причины

Сейчас `TMC2209Motor` сваливает всё в `invalid response: ''`, поэтому по логам
пустой ответ (таймаут) неотличим от обрезанного и от склеенного. Развести на три
разных сообщения — иначе следующий такой баг снова придётся ловить логами вручную.

### 5. Тест на симуляторе

В `src/sim/tmc_sim.py` смоделировать реальную выдачу: побайтовый слив и кольцо на
256 байт с отбрасыванием (это же нужно для этапа хаос-инжиниринга, PLAN.md §3 этап 3б).
Прогнать реальный паттерн опроса из `logs/` и проверить, достижимо ли переполнение
до правок и недостижимо ли после.

## Порядок и проверка

1. Тест на симуляторе, воспроизводящий переполнение (красный).
2. Правки 1–3 в прошивке → тест зелёный.
3. Правка 4 на хосте.

**Ограничение**: всё перечисленное я могу проверить только на симуляторе. Реальная
верификация требует перепрошивки DEC-контроллера и прогона на живом железе — это
остаётся за владельцем стенда. Отдельно на железе стоит проверить пункт 1: не вырос ли
джиттер шагов при сливе пачкой.

## Что осталось за рамками

Обрезанные ответы `'=1'` и `'7E#'` в логах — это **RA-канал SkyWatcher**, чужая
прошивка; к этому буферу они отношения не имеют. Наш DEC-контроллер в логах даёт
только `invalid response: ''` (70 раз за сессию), то есть пустые ответы, а не обрезанные.
Иначе говоря, описанный дефект реален, но в собранных логах ещё не проявился — правки
здесь профилактические. Причину обрезанных ответов RA (USB-переходник PL2303, питание,
сама плата) надо искать отдельно.

## Продолжение после ремонта UART — 2026-07-26

Предыдущий план TX-кольца выполнен и проверен на плате. После перепайки PDN_UART
TMC2209 отвечает на 19200 и 38400 бод; основная прошивка использует 19200.

Следующая сборка добавляет:

1. опрос `DRV_STATUS` раз в секунду;
2. при `OTPW` — ток 400 мА вместо 600 мА и предел 1000 логических шагов/с;
3. при `OT`/short — немедленное отключение EN; при двух потерях UART подряд —
   торможение по рампе и отключение;
4. поля защиты и активного микрошага в status v3, журналирование на хосте;
5. полный шаг на дальней части target-хода и возврат к `fine_mres` до зоны
   торможения плюс 32 полных шага;
6. `cs_actual` и расчётный `current_ma_est` в `full_status`.

Точных ватт нет: плата измеряет VM, но не входной ток. `CS_ACTUAL` — управляющий
масштаб фазного тока, поэтому VM × `current_ma_est` не является мощностью источника.

После ручного нагрузочного прогона добавлен StallGuard-контур. На установившемся
ходу от 500 логических микрошагов/с он опрашивает `SG_RESULT` раз в 200 мс после
800 мс разгона. Значения `<=8` дают три балла нагрузки, `9…20` — один, `>=40`
снимает один; при шести баллах валидный `DRV_STATUS` подтверждает живой UART,
после чего прошивка защёлкивает `drv_flags=0x10`, увеличивает `events`, немедленно
снимает EN и остаётся в `shutdown`. Явный `enabled 0` подтверждает стопор и
разрешает следующий запуск, не очищая независимые тепловые/силовые/UART-аварии.

Повышение тока при стопоре отложено до идентификации паспортного тока двигателя:
600 мА уже дают `CS_ACTUAL=18` / расчётные 581 мА фазного RMS, а безопасный верхний
предел подключённого мотора в проекте не указан.

## Следующий аппаратный шаг — DIAG → D2

Живой тест 2026-07-27 показал, что описанный выше UART-контур **не является
надёжной защитой от стопора**. Свободный ход дал `SG_RESULT=16…120`, удержание
вала — практически пересекающийся диапазон `16…122`; защёлка `drv_flags=0x10`
не сработала. Причина в частоте наблюдения: `SG_RESULT` обновляется раз в полный
шаг, а значимый переход при потере синхронизации короткий и опрос раз в 200 мс
может его полностью пропустить.

Следующий шаг, когда будет возможность паять:

1. соединить выход `DIAG` TMC2209 со свободным входом прерывания `D2` Arduino Nano;
2. настроить `TCOOLTHRS` для нижней границы надёжной скорости StallGuard4 и
   откалибровать `SGTHRS` на этом моторе;
3. в обработчике прерывания только защёлкнуть факт импульса, а остановку,
   диагностику и внешний статус выполнить в основном цикле;
4. голосом предупредить перед запуском, повторить свободный и нагрузочный прогоны,
   проверить `drv_flags=0x10`, `events+1`, немедленное снятие EN и явное
   подтверждение через `enabled 0`;
5. отдельно проверить низкие точные скорости: если StallGuard4 там нестабилен,
   для гарантированного обнаружения потери шагов потребуется энкодер.

До выполнения этого шага мотор оставлять выключенным. Ток выше 600 мА не поднимать.

Предыдущая стендовая проверка (2026-07-27): PlatformIO `nanoatmega328` — RAM 1857/2048,
Flash 28102/30720; общий C++ selftest кадра прошёл; весь Python-набор —
603 passed, 1 xfailed; ruff и mypy чистые. Прошивка залита и verified,
