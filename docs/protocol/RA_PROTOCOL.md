# Протокол платы SkyWatcher, ось RA — снято с живого железа

Документ описывает **фактическое** поведение конкретной платы. Каждое утверждение
ниже подкреплено дословным ответом платы из трасс в `logs/protocol/ra_*.jsonl`.
Там, где проверки не было, это сказано явно.

## 2. Идентификация платы и константы

| Запрос | Дословный ответ | Декодирование (Revu24, §4.5) | Значение |
|---|---|---|---|
| `:e1\r` | `=03110A\r` | `0x0A1103` → перестановка байт → `0x03110A` | прошивка **0x0311**, mount code **0x0A** |
| `:a1\r` | `=729DBE\r` | `0xBE9D72` | **CPR = 12 492 146** отсчётов/оборот |
| `:b1\r` | `=0024F4\r` | `0xF42400` | **TMR_Freq = 16 000 000 Гц** |
| `:g1\r` | `=01\r` | 8-битный формат, прямой порядок | **highspeed ratio = 1** |
| `:D1\r` | `=17AF01\r` | `0x01AF17` | **период 1× трекинга = 110 359** |
| `:c1\r` | `=544200\r` | `0x004254` | brake steps = 16 980 (0.489°) |
| `:s1\r` | `=000000\r` | `0x000000` | PEC period = 0 |
| `:h1\r` | `=000080\r` | `0x800000` | goto target = логический ноль |
| `:d1\r` | `=000080\r` | `0x800000` | Tele. Axis Position |

**Один отсчёт = 0.1037″** (360·3600 / 12 492 146).

**Проверка на согласованность.** `TMR_Freq · сид.сутки / CPR = 16·10⁶ · 86164.09 / 12 492 146
= 110 359.4`, а плата в `:D1` сама сообщает `110 359`. Формула §3.2 спецификации
подтверждена железом с точностью до округления.

### 2.1 Разрядность ответа `:g1` — 2 символа, не 6

Плата отвечает `=01\r`, то есть **два** hex-символа. Это ровно то, что предписывает
спецификация (`Response D` = 2 символа, §5.3), но **референсная реализация
`skywatcher.cpp` этого не учитывает**: `RAHighspeedRatio = Revu24str2long(response+1)`
читает шесть символов из четырёхсимвольного буфера. На такой плате референс
прочитал бы мусор за границей строки. Драйвер проекта делает правильно —
`_Revu24.from_mount(..., hex_chars=2)`.

Значение `1` само по себе противоречит спецификации: §3.3 утверждает, что N
«может быть 16, 32 или 64». На этой плате высокоскоростной множитель отсутствует
(см. §10.4).

### 2.2 Mount code 0x0A и `min_period`

`mount_code = 0x0A`. В таблице `references/skywatcher.cpp` (`InquireBoardVersion`)
кода `0x0A` **нет**: перечислены `0x00 EQ6`, `0x01 HEQ5`, `0x02 EQ5`, `0x03 EQ3`,
`0x80 GT`, `0x81 MF`, `0x82 114GT`, `0x90 DOB`, `0xF0 GEEHALEL`. Всё остальное
попадает в `default: CUSTOM` с `minperiods = 6`.

В драйвере проекта было `0x0A -> 0x0600 = 1536`. Источник этого числа не найден
ни в референсе, ни в спецификации, ни в приложении вендора (`rpsToStride` в
SAM Console не зажимает вообще, `RA_SA_CONSOLE_PROTOCOL.md`). Таблица убрана:
драйвер теперь **измеряет** предел у самой платы парой `:I1`/`:i1` при
подключении (§10.5) и восстанавливает исходный период.

Что из этого следует численно:

| `min_period` | Макс. скорость оси | В сидерических |
|---|---|---|
| 6 (референс, `CUSTOM`) | 76.85 °/с | 18 393× |
| **1536 (драйвер проекта, код 0x0A)** | **0.3002 °/с** | **71.8×** |
| **1103 (реальный предел самой платы, §10.5)** | **0.4180 °/с** | **100.05×** |

Вывод: `min_period = 1536` **не был опасен** — он строже, чем собственный предел
платы, — но оставлял неиспользованными 28 % диапазона. Хуже другое: при
`_HIGHSPEED_SPEED = STELLAR_SPEED · 800` расчётный период 137 зажимался до 1536,
а наверх, в `get_speed_sps_by_delta`, уходили запрошенные 800×. Ось считала по
ним ETA для GOTO и вычитала дрейф неба за эту ETA — то есть **GOTO шёл в 11 раз
дольше, чем считала ось, и компенсация неба была во столько же раз меньше
нужной**. Исправлено: наверх уходит достижимая скорость (запрос прогоняется
через тот же круг «скорость → период → кламп → скорость», что и железо).
Референсное значение 6 было бы бессмысленным по другой причине: плата всё равно
зажимает период на 1103.

### 3.1 `:m1` — производная величина, а не константа

> **Опровергнуто на железе, `RA_PROTOCOL_STEP_2.md` §2.2.** `:m1` считается от
> **цели** (`:h1`), а не от позиции. Оба замера ниже сняты при позиции и цели,
> равных `0x800000`, и различить их не могли. `:M1` (Set Break Point Increment)
> при этом не делает ничего: величина торможения жёстко равна `:c1`.

`brake point = позиция ± brake steps`, знак берётся от последнего направления.
Проверено численно:

* в начале сессии: `:m1` = `=ACBD7F` = `0x7FBDAC`; позиция `0x800000`;
  `0x800000 − 0x7FBDAC = 0x4254 = 16 980` = ровно `:c1`;
* после прогонов: `:m1` = `=544280` = `0x804254`;
  `0x804254 − 0x800000 = 0x4254 = 16 980` — то же число, другой знак.

Три подряд идущих чтения дали `=544280` без изменений, то есть величина
стабильна и меняется только вслед за движением/направлением.

### 3.2 Канал `2` и прочие каналы

Плата отвечает на любой **hex-символ** в позиции канала. Только `1` — реальная ось:

| Команда | Ответ |
|---|---|
| `:e2\r` | `=03110A\r` |
| `:a2\r` | `=729DBE\r` |
| `:j2\r` | `=000080\r` |
| `:f2\r` | `=000\r` |
| `:f3\r` | `=000\r` |
| `:f0\r` | `=000\r` |
| `:f4\r` | `=000\r` |
| `:f9\r` | `=000\r` |

То есть канал `3` («Both» по спецификации, note *1) **не** обрабатывается особым
образом: `:f3` возвращает то же, что `:f2`. Нехексовый символ канала даёт `!3`
(`:f?` → `!3`, `:fL` → `!3`).

**Практический вывод для драйвера:** ошибиться каналом невозможно «громко» —
плата не ругается, а молча отвечает статусом несуществующей оси `=000`
(«не инициализирована, стоит, режим Goto»). Драйвер обязан жёстко фиксировать
канал `1`, потому что диагностики от платы тут не будет.

## 5. Расширенный запрос `:q` — документированные и недокументированные ID

**Формат аргумента.** ID передаётся в том же перевёрнутом порядке Revu24, что и
любые 24-битные данные: ID `0x000001` уходит как строка `010000`, то есть команда
`:q1010000\r`. Именно так формирует её референсная реализация
(`long2Revu24str` + `dispatch_command(GetFeatureCmd, ...)`).

Раньше в проекте пробовали `:ql000000` и `:qL000001` — там на месте **канала**
стоят буквы `l`/`L`, поэтому плата и отвечала `!3` (Invalid Character). Это была
ошибка обрамления, а не отсутствие поддержки.

Перебор: младший байт ID `0x00`–`0xFF`, средний байт `0x00`–`0x0F`, старший байт
`0x00`–`0x0F`. Отвечают ровно пять ID, все с младшим байтом 1..5:

| Команда | Ответ | Revu24 | Стабильность |
|---|---|---|---|
| `:q1000000\r` | `!0\r` | — | документированный ID 0 не поддержан |
| `:q1010000\r` | `=008000\r` | `0x008000` | константа (5/5 замеров) |
| `:q1020000\r` | `=100000\r` | `0x000010` = 16 | константа (5/5) |
| `:q1030000\r` | `=D30102\r` / `=D40102\r` | `0x0201D3` / `0x0201D4` | **дрейфует**, см. §6.3 |
| `:q1040000\r` | `=A3C9CA\r` | `0xCAC9A3` | константа (5/5) |
| `:q1050000\r` | `=49DB48\r` | `0x48DB49` | константа (5/5) |
| `:q1060000\r` … `:q1FF0000\r` | `!0\r` | — | не поддержаны |

### 5.1 Status EX (`:q1010000` → `=008000`)

Читаем по таблице §5.8 спецификации: возвращённые символы это Byte0…Byte5 =
`0 0 8 0 0 0`.

| Байт | Значение | Расшифровка по §5.8 |
|---|---|---|
| Byte0 = `0` | 0 | PEC Training выкл., PEC Tracking выкл. |
| Byte1 = `0` | 0 | нет dual encoder, нет PPEC, **нет original position indexer**, нет EQ/AZ mode |
| Byte2 = `8` | B3 = 1 | B0 (polar scope LED) = 0, B1 (оси стартуют раздельно) = 0, B2 (выбор момента трекинга) = 0, **B3 спецификацией не определён** |
| Byte3…5 = `0` | 0 | зарезервировано |

Единственный поднятый бит — Byte2 B3, то есть бит `0x8000` в 24-битном значении.
Спецификация его не описывает. В `references/skywatcher.h` объявлена структура
`SkyWatcherFeatures`, последнее поле которой — `hasWifi`; по порядку полей этот
бит соответствует именно ему. **Но подтвердить это по файлам репозитория нельзя:**
`skywatcher.h` объявляет `InquireFeatures()`, а `skywatcher.cpp` (более старая
версия) её **не реализует** — маски битов в репозитории отсутствуют. Поэтому
трактовка «has WiFi» — гипотеза, а факт — «поднят Byte2 B3, спецификацией не
описанный».

Что подтверждено фактически и без гипотез: **у платы нет ни PPEC, ни второго
энкодера, ни индексатора home-позиции, ни LED полярного искателя.**

## 6. Как на самом деле получить напряжение питания

> **Итог на 2026-07-25, вечер: напряжение читается. Это окно `:C`/`:n`,
> адреса `0x0004` (батарея) и `0x001C` (USB), int16 little-endian, делить
> на 100 → вольты.** Команду нашли не перебором, а разбором APK вендорского
> приложения SAM Console (`RA_SA_CONSOLE_PROTOCOL.md`), после чего проверили
> на живом железе — числа и трасса в §6.8.
>
> Разделы §6.1–§6.7 оставлены нетронутыми: это ход поисков, включая ложный
> след `:q1030000` и его опровержение. Читать их надо, помня итог. Важно, что
> ответ **лежал в наших же данных**: §6.2 зафиксировал «в окне ненулевые
> только 0x04, 0x05, 0x1C, 0x1D» и не смог их прочитать, а §6.3 верно
> заметил, что `:q1030000` дублирует 0x1C/0x1D — это USB-канал, а не батарея,
> и полное 24-битное значение вольтами не является.

### 6.1 Откуда взялась `:fL#` и почему она не могла работать

* Команда добавлена коммитом **`9d38f3c` «[AI] Prettier dashboard output»** (2026-03-15)
  вместе с `get_power_v()` и полем `power_v` на дашборде.
* В спецификации SkyWatcher (полный текст PDF, 325 строк) слов
  `volt`, `power`, `battery`, `supply`, `diagnos` **нет вообще**.
* В `references/skywatcher.cpp` / `.h` слова `volt` / `battery` / `Vcc` нет;
  единственное вхождение `Power` — строка отладочного лога «Powering motors».
* В `references/LX200CommandSet.txt` команды `fL` тоже нет.
* Обрамление `:fL#` противоречит формату платы (`:<cmd><channel><data>\r`):
  `L` стоит на месте канала и не является hex-символом.

Железо это подтверждает напрямую: **`:fL\r` → `!3\r`** (Invalid Character) —
плата разбирает `L` именно как недопустимый символ канала. А `:fL#` без `\r`
не завершает команду вовсе, поэтому плата молчит все 507 мс таймаута.

Ещё проверено: терминатор `#` не работает и для заведомо валидных команд —
`:f1#` и `:e1#` тоже дают пустоту. Плата отвечает **только** на `\r`.

**Вывод: `:fL#` — команда из чужого протокола, на этой плате она не могла
работать никогда.**

### 6.2 Что перебрано в поисках напряжения

| Что | Результат |
|---|---|
| `:fL#`, `:fL\r`, `:f1#`, `:e1#` | пусто / `!3` |
| Расширенный запрос `:q1` — ID `0x000000`–`0x0000FF` (младший байт) | отвечают только 1..5 |
| Расширенный запрос `:q1` — средний байт `0x00`–`0x0F` | все `!0` |
| Расширенный запрос `:q1` — старший байт `0x00`–`0x0F` | все `!0` |
| Все неиспользуемые буквы команд (`X Y Z l o p t u v w x y`) | все `!0` |
| Регистровый файл: `:A1<addr>` + `:r1`, адреса `0x00`–`0xFF` (256 адресов) | **все 256 читаются как `=00`** — окно-заглушка |
| EEPROM: `:C1<addr>` + `:n1`, адреса `0x00`–`0x1F` | ненулевые только 0x04=`5D`, 0x05=`02`, 0x1C, 0x1D |
| Полный текст PDF на предмет команд питания/диагностики | нет таких команд |
| `references/skywatcher.cpp` / `.h` на предмет чтения напряжения | нет такого кода |

### 6.3 Единственный кандидат — и почему он не подошёл

`:q1030000` возвращает медленно дрейфующее число около `0x0201D3` = 131 539.
Это единственная живая аналоговая величина, найденная на плате. Проверки:

* **Мгновенный шум отсутствует.** 40 замеров подряд (≈0.2 с) дали
  `131540` без единого отклонения — span 0. То есть это не шумящий АЦП,
  а медленно обновляемая величина.
* **Дрейф на масштабе минут.** За сессию (≈15 мин) значение прошло диапазон
  `131497 … 131540`, то есть ±20 отсчётов вокруг 131 530.
* **На нагрузку мотора не реагирует.** Прогоны на 1×, 16×, 64× и 128× сидерических
  с плотной выборкой во время движения: на 128× вперёд все 18 замеров во время
  вращения дали ровно `131540` — то же значение, что в покое до старта.
  Просадки при движении **нет**.
* **Дублируется в окне `:C1`/`:n1`.** Адреса 0x1C/0x1D содержат младшие 16 бит
  того же числа и меняются с ним синхронно. Проверено шестью замерами через
  секунду: `D3 D3 D3 D4 D4 D3` в `:q1030000` и ровно `D3 D3 D3 D4 D4 D3` в
  «EEPROM» 0x1C, при 0x1D = `01` всё время. То есть `:C1`/`:n1` — не EEPROM,
  а окно во внутреннее ОЗУ.

**Итог: это не напряжение питания.** Величина, которая не меняется при
включении мотора, не может быть напряжением на плате, которая, по словам
владельца, от нагрузки мотора уходит в перезагрузку. Калибровки нет, физический
смысл не установлен.

### 6.5 Напряжение всё-таки читается: `:q1030000`, младший байт

Ошибка предыдущего вывода была методической: величину проверяли на **вращении
без физической нагрузки**. Star Adventurer на холостом ходу потребляет так мало,
что просадка тонет в разрешении. Стоило нагрузить ось рукой — сигнал проявился.

**Формат.** Ответы имеют вид `=XX0102`: старшие два байта всегда `0x0201`,
меняется только младший. Полезная величина — одно число, `0xA6`…`0xCF`.

**Опыт 1 — нагрузка рукой** (4617 замеров, 64× сидерических, владелец то
усиливал, то ослаблял давление):

| Фаза | Значение |
|---|---|
| покой | 204–206, разброс 2 единицы за 366 замеров |
| вращение под меняющейся нагрузкой | 166–205 |

Просадка до **19%**, и её профиль во времени повторяет циклы нажатий: провал до
166 на нажатии, возврат к ~190 при отпускании, снова провал.

**Опыт 2 — контрольный, без нагрузки** (9758 замеров):

| Фаза | min | max | среднее |
|---|---|---|---|
| покой до | 206 | 207 | **206.1** |
| вращение, ось не трогали | 188 | 207 | **194.4** |
| покой после | 193 | 207 | **206.3** |

Просадка масштабируется с потреблением — 12 единиц от холостого вращения, 40 от
вращения под рукой, — и **полностью восстанавливается** при снятии нагрузки.
Это и есть подпись измерителя напряжения питания.

### 6.6 Калибровка

Опорная точка снята мультиметром 2026-07-25 одновременно с чтением регистра:

> **187 единиц ↔ 6.09 В**, то есть **32.57 мВ на единицу**.

| Состояние | counts | вольт |
|---|---|---|
| покой в начале сессии | 206 | 6.71 |
| вращение вхолостую | 194 | 6.32 |
| покой после серии прогонов | 187 | 6.09 |
| под нагрузкой рукой | 166 | 5.41 |
| полная шкала `0xFF` | 255 | 8.30 |

Просадка: **0.39 В** от холостого вращения, **1.30 В** под нагрузкой.

**Что подтверждает калибровку.** Star Adventurer 2i питается от **4×AA**;
6.71 В — свежий щелочной комплект, 6.09 В — подсевший. Регистр упал на 19
единиц (0.62 В) за время наших прогонов, то есть отследил разряд батарей в
реальном времени. Полная шкала 8.30 В — разумный запас над номиналом 6 В.

**Оговорка: точка одна.** Масштаб выведен через ноль, то есть предполагает
отсутствие смещения. Вторая точка (замер под нагрузкой или после разряда)
проверила бы линейность и смещение; до этого считать масштаб приближённым.

**Порог броунаута.** Плата стабилизирует питание в 5 В. При нынешних 6.09 В
такая же нагрузка, какую давал владелец рукой, утащит питание к **4.79 В** —
ниже того, что нужно регулятору. Это и есть механизм отказа из §12,
подтверждённый числами: «даёшь команду, нагружается мотор, питания не хватает,
и он сбрасывается».

**Почему это важно.** Владелец описывает отказ так: «даёшь команду, нагружается
мотор, питания не хватает, и он сбрасывается». Этот регистр — единственный
способ увидеть просадку **до** перезагрузки, то есть ранняя диагностика того
самого отказа, а не украшение дашборда.

### 6.7 Опровержение: `:q1030000` — не напряжение

Гипотеза §6.5 проверена прямыми парными замерами (мультиметр на батарейках,
регистр в тот же момент). **Она не подтвердилась.**

| Батарейки | Мультиметр | Регистр в покое |
|---|---|---|
| рабочие | 6.09 В | 187 |
| рабочие | 6.09 В | 206–207 |
| рабочие | 6.092 В | 211–212 |
| старые | 5.66 В | 207–209, через 25 с 188–196 |
| старые | 5.66 В | 212–213 |

Диапазоны рабочих и старых батареек **полностью перекрываются**; на одном и том
же комплекте значение самопроизвольно гуляет от 187 до 212. Разница напряжения
в 0.43 В не даёт никакого разделения. Дополнительно: во время вращения регистр
падал на 16 единиц (по «калибровке» это 0.5 В), а мультиметр в тот же момент
показывал падение на **0.01 В** — то есть на клеммах просадки нет.

**Почему ошибка возникла.** Калибровка строилась по одной точке через ноль, а
единственным подтверждением служила согласованность знаков: значение падало под
нагрузкой и восстанавливалось в покое. Этого достаточно, чтобы величина
коррелировала с работой мотора, но недостаточно, чтобы она была напряжением.
Урок: одна точка не калибрует ничего, а «ведёт себя правдоподобно» — не
доказательство.

**Что о регистре известно достоверно** (воспроизводится во всех прогонах):

* при вращении падает на 12–40 единиц, после остановки возвращается;
* при вынутых батарейках — ровно `0`, при этом плата работает от USB и крутит
  мотор (подтверждено: 1336 замеров подряд со статусом «в движении»);
* в покое медленно дрейфует десятками секунд, немонотонно;
* с напряжением на клеммах не коррелирует.

Медленное восстановление после нагрузки и дрейф с постоянной времени в десятки
секунд больше похожи на **температуру**, чем на напряжение: напряжение
восстанавливается мгновенно. Гипотеза не проверена — для проверки нужен
контролируемый нагрев или охлаждение платы.

### 6.8 Найденная команда: окно `:C`/`:n`

**Источник.** Статический разбор `libQtSAMApp` из APK вендора
(`RA_SA_CONSOLE_PROTOCOL.md` §2): `SAMSync::readPowerStatus()` читает
`readInt16(0x0004)` и `readInt16(0x001C)`, делит оба на `100.0` и кладёт в
свойства `batteryVolt` / `usbVolt`; UI показывает `Math.max` из них.
`EEPROMConverser::readInt16` — это два байта через окно.

**Формат, проверенный на проводе**
(`logs/protocol/ra_appvolt_2026-07-25_18-53-57.jsonl`):

```
-> :C10400\r      установить адрес окна = 0x0004 (младший байт адреса первым!)
<- =\r
-> :n1\r          прочитать байт по текущему адресу
<- =5C\r          ровно 4 байта: '=', две hex-цифры, '\r'
-> :C10500\r
<- =\r
-> :n1\r
<- =02\r

raw = 0x02 << 8 | 0x5C = 604    ->    604 / 100 = 6.04 В
```

Автоинкремента **нет**: адрес приходится переустанавливать перед каждым байтом.

| Величина | Адреса | Формула |
|---|---|---|
| напряжение батарей | `0x04` младший, `0x05` старший | int16 LE, /100 → вольты |
| напряжение USB | `0x1C` младший, `0x1D` старший | то же |

**Измерено на живой плате** (батарейки 4×AA и USB подключены одновременно):

| Что | Ответы платы | Число | Вольт | Контроль |
|---|---|---|---|---|
| батарея | `0x04` = `5C`/`5D`, `0x05` = `02` | 604–605 | **6.04–6.05** | мультиметр в тот же момент **6.08 В** |
| USB | `0x1C` = `D6`/`D7`, `0x1D` = `01` | 470–471 | **4.70–4.71** | — |

Стабильность: 30 замеров за 30 с — у батареи разброс 1 LSB, у USB 0. Это
настоящее измерение, а не шум. Полный обход окна (адреса `0x00`–`0x3F`) дал
ненулевыми ровно четыре байта — те самые `0x04`, `0x05`, `0x1C`, `0x1D`, то есть
дамп §6.2 воспроизвёлся дословно.

**Связь с §6.3 и §6.7.** Младшие 16 бит `:q1030000` побайтово равны `0x1C`/`0x1D`
(в трассе: `:q1030000` → `=D60102` при `0x1C` = `D6`, `0x1D` = `01`). То есть
старый «единственный кандидат» — это USB-канал, взятый вместе с посторонним
старшим байтом; вольтами полное 24-битное число не является, и калибровка §6.6
(32.57 мВ на единицу) остаётся опровергнутой.

**Что доказано, а что нет:**

* доказано — шкала «/100» для батарейного канала в одной точке около 6 В
  (604 против 6.08 В мультиметра, расхождение 0.7 %); стабильность обоих
  каналов; совпадение `:q1030000` с окном;
* предположение — что `0x1C`/`0x1D` это именно шина USB (основания: имя
  свойства `usbVolt` в APK и правдоподобные 4.7 В), и что в шкале нет
  смещения (точка одна, наклон проведён через ноль).

### 6.4 Что делать драйверу

1. `SkyWatcherMotor.get_power_v()` читает окно: четыре пары `:C1`+`:n1` — два
   байта батареи и два байта USB — и возвращает `max(battery, usb)`, как и UI
   вендора. Плата питается от того источника, который выше, и именно его видит
   стабилизатор; при питании только от USB батарейный канал читается нулём, и
   «0.00 В» было бы ложной тревогой. Оба канала по отдельности видны в
   `protocol_monitor()` и в строке `ra_rail` дашборда, чтобы максимум не прятал
   просевшую батарею при живом USB.
2. Одно чтение — **восемь** команд, а дашборд опрашивает каждый тик, поэтому
   обязателен кэш. В драйвере TTL 5 с по инжектируемым часам: питание, которое
   успевает утащить плату в перезагрузку (§12), проседает за секунды, а не за
   миллисекунды.
3. Отказ платы (`!код`, мусор, короткий ответ) — не исключение наверх, а `None`
   и бэкофф 60 с. Без бэкоффа это была бы та же история, что с `:fL#` (§6.1),
   только в восемь раз шире.
4. Напряжение DEC берётся с платы DEC (`status`, поле `power_v`) — это не
   отменяется, теперь просто есть и RA.
5. Симулятор `src/sim/skywatcher_sim.py` моделирует окно с дефолтами 604 и 470,
   **без** автоинкремента адреса. Выдумки `:fL#` c ответом `<2 hex>#` в нём
   больше нет: живая плата на `:fL#` молчит, а на `:fL\r` отвечает `!3`.

## 7. Коды ошибок: какой ввод какой код вызывает

Формат ответа — `!` + код + `\r`. На практике код **однознаковый** (`!0\r`,
4 байта), тогда как §4.4 спецификации обещает **два** символа кода
(`!` + 2 символа + `\r`, 4 байта). Это расхождение — см. §11.

### Воспроизведённые коды

| Код | Смысл | Чем вызывается — проверено |
|---|---|---|
| `0` | Unknown Command | `:X1\r`, `:x1\r`, `:Y1\r`, `:Z1\r`, `:l1\r`, `:o1\r`, `:p1\r`, `:t1\r`, `:u1\r`, `:v1\r`, `:w1\r`, `:y1\r` — любая неизвестная буква команды |
| | | `:k10\r` — документированная, но не реализованная команда |
| | | `:q1000000\r` … `:q1FF0000\r` — неподдерживаемые ID расширенного запроса |
| | | `:f\r` — команда без байта канала |
| | | `:\r` — пустая команда, только двоеточие и CR |
| `1` | Command Length Error | `:I1\r` — сеттер без аргумента |
| | | `:I112\r` — 2 hex вместо 6 |
| | | `:I100000000\r` — 8 hex вместо 6 |
| | | `:G1\r`, `:G1123456\r` — неверная длина аргумента `G` |
| | | `:j1000000\r` — аргумент у запроса, который его не принимает |
| | | `:f11\r` — один лишний символ |
| | | `:I1` + 40 нулей `\r` — сверхдлинный аргумент |
| | | `:` + 60 символов `A` `\r` — 60 символов мусора |
| `2` | Motor not Stopped | `:G111\r`, отправленная во время вращения оси |
| `3` | Invalid Character | `:IZZZZZZ\r`, `:I1ZZZZZZ\r` — не-hex аргумент |
| | | `:I1abcdef\r` — **hex в нижнем регистре** |
| | | `:I1-00000\r` — минус в аргументе |
| | | `:I1 00000\r` — пробел в аргументе |
| | | `:f?\r`, `:fL\r` — не-hex символ канала |

Отдельно: **буквы `a`–`f` в аргументе должны быть в верхнем регистре.**
`:I1abcdef\r` → `!3\r`. Спецификация пишет «`'0'`–`'9'`, `'A'`–`'F'`», но не
подчёркивает, что нижний регистр запрещён; на железе это жёсткое требование.
Драйвер проекта безопасен: `_Revu24.from_int` делает `.hex().upper()`.

### Коды, которые вызвать НЕ удалось

| Код | Смысл | Почему не удалось |
|---|---|---|
| `4` | Not Initialized | **Плата не проверяет флаг инициализации.** В состоянии `=100` (флаг сброшен) команды `:J1`, `:E1000080`, `:G110` приняты с ответом `=\r`. Флаг у этой платы — только индикатор, а не защита |
| `5` | Driver Sleeping | `:B11` (Set Sleep) принят с `=\r`, но статус не изменился (`=101` до и после), а `:J1` и `:I1...`, отправленные «во сне», тоже приняты с `=\r` и движение после пробуждения состоялось. Спящее состояние на этой плате не наблюдаемо через протокол |
| `7` | PEC Training is running | у платы нет поддержки PPEC (Status EX, §5.1). Запускать PEC-тренировку через `:W1` не пробовал сознательно: это команда записи с неизвестным на этой прошивке эффектом |
| `8` | No Valid PEC data | то же |

## 8. Поведение на кривом входе и обрамление

| Ввод | Ответ платы | Вывод |
|---|---|---|
| `:f1` (без CR) | *(тишина, 0.6 с)* | ответа нет, пока не придёт CR |
| затем одиночный `\r` | `=100\r` | CR довершает ранее отправленную команду |
| `:f` затем `:j1\r` | `=000080\r` | второе `:` отбрасывает недобранную команду — §4.1 подтверждён |
| `\r` (только CR) | *(тишина, 514 мс)* | без ведущего `:` реакции нет |
| `garbage\r` | *(тишина, 507 мс)* | то же |
| `f1\r` (без двоеточия) | *(тишина, 507 мс)* | то же |
| `:\r` | `!0\r` | пустая команда — Unknown Command |
| `:f1\r:j1\r` одной записью | `=100\r` — **и всё** | **вторая команда теряется** |
| `:f1\r`, пауза 20 мс, `:j1\r` | `=100\r=000080\r` | с паузой приходят оба ответа |

### 8.1 Потеря команды в непрерывном потоке — воспроизводимо

Две полные команды, отправленные **одной** записью в порт без паузы, дают
**один** ответ. Проверено 4 раза (3 раза в фазе `flags`, 1 раз в фазе `verify`) —
результат одинаковый: приходит ответ только на первую команду, ожидание 1.5 с
второго ответа не даёт. Те же две команды с паузой 20 мс между ними дают оба
ответа.

Это значит, что плата **не буферизует** вторую команду, пока обрабатывает и
отвечает на первую: байты, пришедшие в это окно, теряются. Требование к
драйверу: между командами обязана быть пауза, и опрос обязан быть строго
«запрос → ответ → запрос». `SerialLine.query` этому удовлетворяет
(`reset_input_buffer` + `write` + `read_until`), но любая попытка конвейеризации
запросов на этой плате сломается молча.

### 8.2 Разбор длины у платы «жадный»

`:` + 60 символов `A` даёт `!1`, а не `!0`, хотя `A` — валидная команда
(Set Register Address). То есть плата сначала распознаёт букву команды, а потом
проверяет длину аргумента. `:f\r` (буква есть, канала нет) даёт `!0`, а не `!1` —
слишком короткий пакет считается неизвестной командой, а не ошибкой длины.

## 10. Движение

Все прогоны — короткими ходами, самый медленный первым, с возвратом оси назад.
Период всегда вычислялся из **измеренных** CPR и TMR_Freq, а не задавался наугад.

### 10.1 Расшифровка статуса `:f1` подтверждена

Ответ — три символа, каждый несёт битовое поле. Подтверждено на живом железе:

| Символ | Бит | Значение | Наблюдение |
|---|---|---|---|
| 1-й | B0 | 1 = Tracking, 0 = Goto | `=1xx` в трекинге, всегда 1 после `K` |
| 1-й | B1 | 1 = CCW, 0 = CW | `:G110` → `=1..`, `:G111` → `=3..` |
| 1-й | B2 | 1 = Fast, 0 = Slow | `=5..` / `=7..` при малом периоде |
| 2-й | B0 | 1 = Running, 0 = Stopped | `=x1x` во время хода |
| 3-й | B0 | 1 = Init done, 0 = Not Init | `=xx1` после `:F1` |

Наблюдённые значения: `=100` (стоит, CW, не инициализирована), `=101`
(стоит, CW, инициализирована), `=111` (идёт, CW, медленно), `=301` / `=311`
(CCW), `=511` / `=711` (идёт, бит Fast поднят).

Порядок байт в `_Status.from_bytes` драйвера (`b1` — режим/направление/скорость,
`b2` — running, `b3` — init) совпадает с железом и с `ReadMotorStatus` референса.

### 10.2 Бит Fast плата поднимает сама, а `:G1 3 x` его не поднимает

Это самое неожиданное наблюдение по статусу:

* `:G110` (запрошен **медленный** трекинг) + период 1724 → в покое `=101`
  (Fast сброшен), **во время хода `=511`** — Fast поднят;
* `:G110` + период 6897 → и в покое, и во время хода `=111` — Fast сброшен;
* `:G130` (запрошен **быстрый** трекинг) + период 1724 → в покое `=101`,
  то есть бит Fast **не** поднимается от самой команды `G`.

Вывод: бит B2 первого символа статуса отражает **фактический режим шага, который
плата выбрала по величине периода**, а не то, что запросил мастер командой `G`.
Порог лежит между периодами 6897 и 1724 (между 16× и 64× сидерических).
Спецификация §5.4 подаёт этот бит как простой отчёт о запрошенной скорости —
на железе это не так.

### 10.3 `K` — торможение с рампой, а не мгновенная остановка

| Скорость | Статус через 0.6 с после `:K1` | Выбег |
|---|---|---|
| 1×, 16×, 64× сидерических | `=101` / `=301` — уже стоит | незаметен |
| 128× сидерических | **`=511` / `=711` — всё ещё Running** | ≈1148 отсчётов (0.033°) после `K` |

Примечание спецификации *4 («после `K` канал всегда в режиме трекинга»)
**не подтверждается** — см. `RA_PROTOCOL_STEP_2.md` §2.4. Все замеры этой
таблицы выходили из режима трекинга, где бит B0 и так стоял, так что
подтверждать было нечего; из режима goto `:K1` режим не меняет.
Выбег тоже перемерен (§2.6 шага 2): на реальном потолке платы он длится
1.05 с и 6 886 отсчётов, а не 0.6 с и 1148.
Ниже — исходные наблюдения первой сессии, как они были записаны.
Направление при этом сохраняется (`=101` после хода CW, `=301` после хода CCW),
а бит Fast сбрасывается вместе с остановкой.

**Требование к драйверу:** после `K` нельзя считать ось остановленной по факту
ответа `=`; нужно опрашивать `:f1`, пока не сбросится бит Running.
`wait_till_stop` в драйвере это делает правильно. А вот `stop()` сам по себе
возвращает `True` немедленно — на 128× это неправда ещё как минимум 0.6 с.

### 10.4 Highspeed ratio = 1: режим `G '3'` ничего не меняет

Один и тот же период 1724 в режиме `:G110` (медленный) и `:G130` (быстрый):

| Прогон | Режим | Период | Отсчётов за ≈3.15 с |
|---|---|---|---|
| `fwd-64x` | `10` | 1724 | 29 856 |
| `hs-64x` | `30` | 1724 | 30 031 |
| `rev-64x` | `11` | 1724 | −29 962 |
| `hs-64x-back` | `31` | 1724 | −29 767 |

Разница в пределах погрешности измерения окна. Скорость от режима `G` **не
зависит**. Это прямое следствие `highspeed ratio = 1`: множителя нет, и вся
логика §3.3 спецификации на этой плате вырождается.

> **Уточнено на железе, `RA_PROTOCOL_STEP_2.md` §2.6.** Формула верна для
> **установившейся** скорости и только до 64×. Выше порога бита Fast плата
> разгоняется рампой ~13 000 шаг/с², а на периоде 1103 идёт 9 015 шаг/с вместо
> обещанных 14 506: собственный потолок платы ≈ 9 000 шаг/с (~62×). Замеры
> ниже сделаны от старта, без поправки на разгон.

Скорость подчиняется простой формуле `шагов/с = TMR_Freq / период`:

| Период | Расчёт, шагов/с | Измерено, шагов/с |
|---|---|---|
| 110 359 | 145.0 | 145 (456 отсчётов за 3.15 с) |
| 6 897 | 2 319.8 | ≈2 320 |
| 1 724 | 9 280.7 | ≈9 478 |

### 10.5 Плата сама зажимает период на **1103**

Проверено записью периода и обратным чтением `:i1` при неподвижной оси, в обоих
режимах `G` (`10` и `30`), 18 значений в каждом:

| Записано | Прочитано обратно |
|---|---|
| 110 359, 20 000, 6 897, 4 000, 2 000, 1 724, 1 536, 1 200, **1 103** | ровно то же самое |
| 1 000, 862, 500, 200, 100, 50, 10, 1, **0** | **1 103** во всех случаях |

То есть плата принимает `:I1` с любым значением, отвечает `=`, но хранит
`max(значение, 1103)`. Ноль тоже превращается в 1103 — деления на ноль
устроить нельзя.

**1103 = 110 359 / 100 (целочисленно).** То есть предел жёстко привязан к
периоду 1× трекинга. Ни спецификация, ни референс такого ограничения не
упоминают.

> **Уточнено, `RA_PROTOCOL_STEP_2.md` §2.6.** Это предел **периода**, а не
> скорости, и до реального предела он не дотягивается: на периоде 1103 ось
> идёт те же ~9 000 шаг/с, что и на 1724, то есть ~62× сидерических, а не 100×
> (14 506 шаг/с). Утверждение «плата не даёт идти быстрее ровно 100×» неверно
> дважды: и «ровно», и «100×».

Следствия: `min_period` на стороне хоста не нужен для безопасности вовсе —
плата защищает себя сама. Значение 1536 в драйвере лишь срезало верхние 28 %
доступного диапазона (71.8× вместо 100×).

**Что делает драйвер.** Вместо таблицы по mount code он спрашивает предел у
платы при подключении, на неподвижной оси: `:i1` (запомнить период), `:I1` с
заведомо малым значением, `:i1` (плата ответит своим минимумом), `:I1` обратно.
Восстановление обязательно: иначе после подключения на плате остаётся самый
быстрый период, и `:J1` откуда угодно стартанул бы ось на 100× вместо трекинга.
Если плата на пробу не ответила — падать назад на референсное 6 и написать в лог,
что сообщаемые скорости могут быть оптимистичны.

### 10.6 Возврат оси

Позиция в начале сессии — `0x800000`. После всех прогонов (шесть низкоскоростных
плеч, два высокоскоростных, два плеча на 128×, серии bisect на 1×) ось вернулась
в пределах нескольких сотен отсчётов, и в финале позиция восстановлена
командой `:E1000080` при **остановленной** оси. Финальное чтение: `:j1` →
`=000080`, `:f1` → `=101`.

## 11. `:E` во время движения асинхронно сбрасывает флаг инициализации

Это единственный найденный дефект прошивки, который выглядел как «плата села».
Разобран до конца, и это **не** броунаут.

### Как обнаружено

В конце фазы `motion` статус внезапно сменился с `=301` на `=100` — сбросился
флаг инициализации. Все команды при этом отвечали нормально за 2–5 мс, потерь
связи не было, позиция не «прыгнула».

### Как локализовано

| Проверка | Результат |
|---|---|
| Повтор всей хвостовой последовательности 5 раз | **5/5 — флаг терялся.** Значит, детерминированный эффект, а не случайный сбой |
| Каждый сеттер (`E S H M U T G I K L P O V z`) по отдельности при **стоящей** оси, с `:F1` перед каждым | ни один флаг не сбрасывает |
| `E`, `S`, `H`, `M`, `I` по отдельности при **идущей** оси | ни один флаг не сбрасывает |
| Отвергнутая команда (`:G111` → `!2`, `:X1` → `!0`) при идущей оси | флаг не сбрасывает |
| `S` → `E` при идущей оси | флаг **не** сбрасывает |
| `E` → `S`, `E` → `E`, `E` → `I`, `E` → `H` при идущей оси | флаг теряется |
| `E`, затем **просто пауза 1 с** при идущей оси | флаг теряется |
| `E`, затем только запросы (`:j1`, `:f1`) | флаг сохраняется |
| Повтор той же комбинации `E` → `E` в другом заходе | флаг **сохранился** |

### Вывод

Триггер — **`:E` (Set Position), отправленная при вращающейся оси**. Спецификация
для `E` требует «Motor must be full stopped», но плата **не** возвращает `!2` —
она принимает команду с `=\r`. После этого флаг инициализации сбрасывается
**асинхронно, с задержкой в сотни миллисекунд**; успеет ли он сброситься до
конкретного чтения `:f1` — зависит от того, сколько прошло времени, поэтому
одна и та же последовательность в разных заходах даёт разный результат.

### Требования к драйверу

1. Никогда не слать `:E` при поднятом бите Running. `SkyWatcherMotor.set_steps`
   уже поднимает `MotorStopRequire`, если ось идёт, — это правильно и должно
   таким остаться.
2. Не полагаться на `!2` как на защиту: плата её здесь **не** возвращает,
   проверка обязана быть на стороне хоста.
3. После любого `:E` перечитывать `:f1` и при сброшенном флаге инициализации
   слать `:F1` заново.
4. Из-за асинхронности проверять флаг не сразу, а с задержкой, иначе проверка
   пройдёт до того, как флаг успеет сброситься.

## 12. Броунаут: механизм, признаки, как отличить от других отказов

По словам владельца, механизм такой: подаётся команда → мотор нагружается →
питания не хватает → контроллер перезагружается. Сброс позиции — следствие
перезагрузки.

**В этой сессии броунаут не наблюдался.** Единственный кандидат оказался
программным квирком `:E` (§11). Значит, всё ниже — не наблюдение, а требования
к драйверу и симулятору, выведенные из подтверждённых свойств платы.

> **Наблюдён на шаге 2** (`RA_PROTOCOL_STEP_2.md` §3): три запуска GOTO из трёх
> уронили плату через 0.06–0.22 с. И там же — поправка к §12.2 ниже: позиция
> после реальной перезагрузки под нагрузкой оказывается **не ровно**
> `0x800000`, а на несколько сотен отсчётов дальше по ходу, потому что ось
> докручивает их уже после сброса счётчика. Проверка «позиция ровно 0x800000»
> настоящую перезагрузку пропускает.

### 12.1 Что известно о состоянии после включения

Плата на старте сессии была ровно в этом состоянии, поэтому оно снято с натуры:

| Величина | Значение после включения |
|---|---|
| `:j1` позиция | `=000080` = `0x800000` — логический ноль |
| `:f1` статус | `=100` — трекинг, CW, стоит, **флаг инициализации сброшен** |
| `:i1` период шага | `=17AF01` = 110 359 — период 1× трекинга |
| `:m1` brake point | цель − brake steps (шаг 2 §2.2) |

### 12.2 Признаки перезагрузки

Проверять надо **совокупность**, потому что каждый признак по отдельности имеет
законное объяснение:

| Признак | Ложные срабатывания, подтверждённые в этой сессии |
|---|---|
| Позиция стала ровно `0x800000` | так же выглядит любой корректный `:E1000080` |
| Флаг инициализации сброшен | сбрасывается квирком `:E`-во-время-хода (§11) без всякой перезагрузки |
| Ответ `!4` на ранее проходившую команду | **не наблюдаем в принципе**: плата не проверяет флаг инициализации и не возвращает `!4` (§7) |
| Период шага вернулся к 110 359 | так же выглядит собственный `:I1` драйвера |

**Надёжный признак — сочетание:** позиция стала точно `0x800000` **и** флаг
инициализации сброшен **и** период шага вернулся к значению `:D1`, причём
драйвер сам ничего из этого не задавал. Одного флага недостаточно.

### 12.3 Как отличить три вида отказа

| Отказ | Что видит драйвер |
|---|---|
| **Перезагрузка платы** | связь жива, ответы приходят за обычные 2–4 мс, но состояние обнулилось до §12.1 |
| **Обрыв связи** | ответов нет вовсе, каждая команда упирается в полный таймаут ≈507 мс; `SerialLine` закрывает линию по `SerialException`/`OSError` |
| **Ошибка команды** | приходит `!код` за те же 2–4 мс, состояние платы не меняется |

Ключ: **время ответа**. Перезагрузка не удлиняет ответы — плата отвечает так же
быстро, просто «другая». Обрыв связи, наоборот, виден только по таймаутам.
Разделять эти случаи по одному лишь содержимому ответа нельзя.

### 12.4 Что должен делать драйвер

1. Держать «ожидаемое» состояние (позиция, флаг инициализации, период) и после
   каждой команды движения сверять с фактическим.
2. При совпадении всех трёх признаков §12.2 — считать, что плата перезагрузилась:
   не продолжать движение, а заново пройти `:F1`, восстановить позицию `:E` при
   **остановленной** оси и заново выставить период.
3. Риск броунаута растёт со скоростью, но верхнюю границу ставит сама плата
   (100× сидерических, §10.5). В этой сессии до 128× запрошенных (фактически
   100×) просадок не было.
4. Признаки не различить, если драйвер не знает, что он сам задавал. Значит,
   `set_steps` / `set_speed` обязаны запоминать последнее записанное значение —
   иначе «позиция равна `0x800000`» неинтерпретируема.

## 14. Что осталось непроверенным и почему

| Что | Почему не проверено |
|---|---|
| Коды ошибок `2` в других контекстах, `7`, `8` | `7`/`8` требуют PEC, которого у платы нет (Status EX). Запуск PEC-тренировки через `:W1000000` — команда **записи** с неизвестным на этой прошивке эффектом; сознательно не отправлял |
| Команды `:W1` (Extended Setting) целиком | то же: это записи, включая «Write flash buffer in RAM to flash ROM» (`000009`). Риск необратимого изменения прошивки не оправдан |
| `:Q155AA` Run Bootloader Mode | переводит плату в загрузчик, откуда она не отвечает по обычному протоколу. Не отправлял |
| `:R1xx` Set Register Value | запись в регистры, назначение которых неизвестно (все читаются как `00`). Не отправлял |
| `:N1xx` Set EEPROM Value | запись в окно ОЗУ, в котором лежит живая величина `:q1030000`. Не отправлял |
| Режим GOTO (`:G12x`/`:G10x` + `:S`/`:H`/`:U` + `:J`) | проверен только режим трекинга. GOTO требует более длинных ходов; при подтверждённом квирке `:E` и неизвестном профиле разгона это лишний риск для платы |
| Физический смысл `:q1030000` | значение не реагирует на нагрузку и не имеет калибровки; определить его без внешнего измерения нельзя |
| Значения `:q1020000` = 16, `:q1040000`, `:q1050000` | константы, назначение неизвестно; ни в спецификации, ни в референсе не описаны |
| Скорости выше 128× запрошенных | плата всё равно зажимает на 100× (§10.5), а выше — рост риска броунаута без новой информации |
| Броунаут как явление | сознательно не провоцировался (прямое указание). Раздел §12 построен на выведенных признаках, а не на наблюдении |
| Поведение при пропадании питания на середине команды | требует физического вмешательства в питание |
| Ось `2` в движении | эта плата ведёт только RA; DEC исследуется отдельно |
| Расширенные ID со старшим байтом выше `0x0F` | перебраны `0x00`–`0x0F`; полный перебор 24-битного пространства ID — 16.7 млн команд, ≈18 часов непрерывного опроса |

## 15. Самопроверка

После составления документа плата опрошена заново фазой `verify` — **37 утверждений**
проверены дословным сравнением с записанным ранее ответом.

**Результат: 35 совпадений, 2 расхождения — оба объяснены и перепроверены отдельно.**

| Расхождение | Записано | Получено при проверке | Объяснение и перепроверка |
|---|---|---|---|
| `:m1` | `=ACBD7F` | `=544280` | Это не константа, а `позиция ± brake steps` (§3.1). Перепроверено: 3 чтения подряд дали `=544280` без изменений, а `=544280 − =000080 = 0x4254` — ровно `:c1`. Первое значение было снято до движений, когда знак направления был другим |
| `:n1` по адресу 0x1C | `=D2` | `=D4` | Величина живая и медленно дрейфует. Перепроверено: 6 замеров с интервалом 1 с дали в `:q1030000` последовательность `D3 D3 D3 D4 D4 D3` и ровно ту же последовательность в `:n1` по 0x1C. Это подтверждает (а не опровергает) утверждение §6.3, что 0x1C/0x1D дублируют младшие биты `:q1030000` |

Ни одно расхождение не касается констант платы, кодов ошибок, обрамления или
таймингов — все они совпали дословно, в том числе:
`:e1` = `=03110A`, `:a1` = `=729DBE`, `:b1` = `=0024F4`, `:g1` = `=01`,
`:D1` = `=17AF01`, `:c1` = `=544200`, `:q1010000` = `=008000`,
`:q1020000` = `=100000`, `:q1040000` = `=A3C9CA`, `:q1050000` = `=49DB48`,
`:q1000000` = `!0`, `:k10` = `!0`, `:X1` = `!0`, `:f` = `!0`, `:` = `!0`,
`:I112` = `!1`, `:j1000000` = `!1`, `:f11` = `!1`, `:I1abcdef` = `!3`,
`:f?` = `!3`, `:fL` = `!3`, `:f2` = `=000`, `:f4` = `=000`, `:z1` = `=`,
`garbage\r` = тишина, `:fL#` = тишина, две команды одной записью = один ответ.

Дополнительно перепроверены в отдельных фазах:
зажим периода на 1103 (18 значений × 2 режима `G`), сброс флага инициализации
командой `:E` во время хода (5/5 воспроизведений + 25 вариантов бисекции),
потеря второй команды в непрерывном потоке (4 повтора).
