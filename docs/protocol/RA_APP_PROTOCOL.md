# Протокол официального приложения SynScan Pro — статический разбор APK

Документ описывает, **какие команды железу шлёт официальное приложение
Sky-Watcher SynScan Pro**: протокол мотор-контроллера и протокол WiFi-модуля.
Всё, что относится к самому телефону (интерфейс, каталоги, серверы приложения
для стороннего ПО), сюда не входит — кроме тех мест, где оно служит
доказательством по вопросу о напряжении.

Все утверждения получены **статическим** разбором: приложение не запускалось,
APK не устанавливался, железо не трогалось.

Каждое утверждение сопровождается адресом в дизассемблере
(`libQtSynScanApp_arm64-v8a.so`, виртуальные адреса секции `.text`) и/или именем
функции из таблицы символов. Там, где вывод — предположение, это сказано явно.

### 1.1 Где на самом деле лежит логика

`classes.dex` (3.9 МБ) — это **только** андроидная обвязка Qt
(`org.qtproject.qt.android.bindings.QtActivity`). Никакой логики протокола там
нет. Вся работа с монтировкой — в нативной библиотеке
`lib/arm64-v8a/libQtSynScanApp_arm64-v8a.so` (17 732 944 байта).

Библиотека **не стрипнута**: полная таблица символов, 46 367 записей,
C++-имена с namespace `SW::`. Это принципиально упростило разбор — классы
`SW::SwCmd`, `SW::SwDevice`, `SW::SwMountAxis`, `SW::SwMCommand`,
`SW::CmdXUtil`, `SW::WMProgrammer` читаются по именам методов.

### 1.2 Инструменты

`jadx` / `apktool` / `baksmali` в системе отсутствуют и **не устанавливались** —
они и не понадобились, потому что цель не в dex.

| Шаг | Инструмент |
|---|---|

| Строки ASCII | `strings` |

### 1.3 Что удалось и что нет

Удалось:

* полностью восстановить формат кадра и функцию кодирования команды;
* перечислить **все** буквы команд, которые приложение вообще умеет отправлять;
* восстановить недокументированное семейство команд `:X` (cmdX) целиком по

* дать однозначный ответ на вопрос о напряжении.

Не удалось:

* восстановить содержимое discovery-пакета, которым приложение ищет монтировку
  в сети (§7.2);
* точно декодировать бинарные полезные нагрузки cmdX (порядок и разрядность
  полей внутри `cmdXEncodeAxisSpeed64`, `cmdXEncodeTime` и т.п.) — восстановлены

## 2. Главный вопрос: как приложение получает напряжение питания

> ## Ответ: **никак. Приложение вообще не читает и не показывает напряжение питания или заряд батарей.**
>
> Ни с мотор-контроллера, ни с WiFi-модуля. Такой функции в SynScan Pro 2.6.10 нет.

Это отрицательный результат, и он закрывает вопрос: искать команду чтения
напряжения по образцу официального приложения бессмысленно — там её нет.

### 2.1 Доказательство 1: в бинарнике нет ни одной строки про напряжение

| Что искал | Где | Результат |
|---|---|---|
| `voltage` (регистронезависимо) | 241 967 строк ASCII из `.so` | **0 совпадений** |
| `volt` | там же | **0 совпадений** |
| `voltage`, `battery`, `power`, `supply`, `vbat`, `adc`, `charge` | 46 367 демангленных символов | **0 совпадений** |
| `Volt` в UTF-16 | 14 653 UTF-16-строки | 1 совпадение: `Voltar a tentar` — португальское «Повторить попытку» |
| `voltage` / `Voltage` по **всем** файлам APK | рекурсивный поиск по байтам | 3 совпадения, все посторонние (см. ниже) |

Три «совпадения» по всему APK:

1. `libplugins_multimedia_ffmpegmediaplugin` — `ADPCM IMA High Voltage Software ALP`,
   название кодека в таблице FFmpeg;
2. `libQt6Bluetooth` — `Tx Power`, `Battery Level` — это **штатная таблица имён
   стандартных GATT-характеристик Bluetooth, которую Qt поставляет со своей
   библиотекой**. Приложение её не использует: в самой `libQtSynScanApp` нет ни
   строковых UUID, ни констант `0x180F`/`0x2A19`;
3. `libQtSynScanApp` — тот самый `Voltar a tentar`.

Единственные вхождения слова `battery` в коде приложения (строки 29456/29460
дампа) — текст диалога *«Ignore Battery Optimization»*, то есть просьба к Android
не убивать приложение в фоне. К питанию монтировки отношения не имеет.

Отдельно проверил `adc`: единственное вхождение — QML-идентификатор `adc` =
сокращение от `alignmentDataContainer` (рядом в том же строковом пуле лежат
`inj_alignmentDataContainer` и `expression for adc`, смещение `0x29f204`).
Ложный след.

### 2.2 Доказательство 2: страница «Информация» не содержит такого поля

Экран «Show Information» наполняется из C++, а не из QML: класс
`SW::GeneralInfoList`, метод **`SW::GeneralInfoList::refresh()` по адресу
`0xb4c5f4`**. Он собирает список строк вызовами `QCoreApplication::translate("mount", ...)`.
Я разрешил все литералы, которые туда передаются. Полный список полей страницы:

```
Coordinates | Azimuth/Altitude | H.A./Dec | R.A./Dec | Axis | Polaris |
Clock Position | Hour Angle | Time | LMST | GMST | Local Time | Greenwich Time |
Alignment | ID | CH | NP | Mel | Maz | Tilt | Align time |
Version | App | Motor Board | Licenses
```

Ни «Power», ни «Voltage», ни «Battery». Конструктор класса тоже красноречив:

```
SW::GeneralInfoList::GeneralInfoList(IAstroCalc, IAstroFormat,
                                     IMountConnection, IAlignmentDataContainer,
                                     IAstroClock)
```

— пять зависимостей, и ни одна не связана с питанием.

### 2.3 Доказательство 3: полный перечень команд приложения не содержит запроса питания

В §5 приведён исчерпывающий список всего, что приложение вообще может послать
мотор-контроллеру. Он получен не поиском по строкам, а разбором **всех** мест,
где конструируется объект команды `SW::SwCmd` (буква команды записывается по
смещению +4 в структуре) и **всех** вызовов фабрик
`SwCmd::extendedInquire` / `extendedSetting` / `x` / `xRead` / `xOperation`.
Ни одна из команд не читает питание.

### 2.4 Доказательство 4: WiFi-модуль тоже не спрашивают о питании

Приложение общается с WiFi-модулем **AT-командами** (класс `SW::WMProgrammer`,
метод `atConversation`). Полный набор — §7.3. Это стандартный ESP-набор
`AT+CWMODE / AT+CWSAP / AT+CWJAP / AT+CWDHCP / AT+CIPSTA / AT+CIPAP`, плюс
неиспользуемые в коде строки `AT+GMR` и `AT+CWMODE_CUR?`. Ни одной команды,
которая читала бы АЦП или напряжение.

### 2.5 Доказательство 5: приложение не отдаёт напряжение и наружу

Побочный факт, но сильный. SynScan Pro поднимает для стороннего ПО
ASCOM-совместимое API (`SW::SSMServer`, версия протокола `SynScan1.0`). Полный
список его команд получен из литералов в `SSMServer::actionSpecs()` и
`SSMServer::CP_*` — 90 с лишним имён вида `RightAscensionGet`, `TrackingSet`,
`GuideRateDeclinationGet`, `SiteLatitudeSet` и т.д. **Ни одной про питание.**
Если бы приложение умело читать напряжение, оно почти наверняка отдавало бы его
в этом API: ASCOM-драйверы такое публикуют охотно.

### 2.6 Что из этого следует для нашего драйвера

1. Гипотезу «официальное приложение как-то умеет — значит, команда существует»
   можно закрыть. Приложение не умеет.
2. Вывод §6 в `RA_PROTOCOL.md` («рабочего способа прочитать напряжение с RA-платы
   не найдено») остаётся в силе и теперь подкреплён вторым, независимым
   источником.
3. Это **не** доказывает, что в прошивке `0x0311` вообще нет такого регистра, —
   доказывает лишь, что вендорское приложение его не читает. Формально
   возможность «регистр есть, но приложение им не пользуется» остаётся, см. §9.

## 3. Формат кадра — подтверждение из кода

Функция **`SW::SwCmd::encode() const`, `0xbba648`**. Структура `SwCmd` в памяти:
`int axis` по смещению 0, `char letter` по смещению 4, полезная нагрузка
(`SW::CBytes`) с 8.

```
bba68c  mov  w10, #0x3a           ; ':'
bba684  ldrb w11, [x20, #0x4]     ; буква команды
bba698  mov  w8,  #0x31           ; '1'
bba6a0  cinc w8,  w8, ne          ; ось != 0  ->  '2'
bba6a4  strb w10, [x0]            ; [0] = ':'
bba6a8  strb w11, [x0, #0x1]      ; [1] = буква
bba6ac  strb w8,  [x0, #0x2]      ; [2] = канал
bba6b8  bl   CBytes::Append       ; [3..] = данные
bba6bc  mov  w8,  #0xd            ; CR
bba6d0  bl   CBytes::Append       ; хвост = '\r'
```

То есть ровно `:<буква><канал><данные>\r`, канал `'1'` для оси 0 и `'2'` для
оси 1. Это в точности то, что мы наблюдаем на проводе, и в точности §4.2
спецификации. Обрамление `#` в приложении **не встречается нигде** — ещё одно
подтверждение §6.1 `RA_PROTOCOL.md` про выдуманную `:fL#`.

### 3.1 Кодирование чисел

| Функция | Что делает |
|---|---|
| `SW::CBytes::Int_B16LE(v, n)` | `n` байт числа `v`, младший байт первым, каждый байт — 2 hex-символа в верхнем регистре |
| `SW::CBytes::Int_B16BE(v, n)` | то же, но старший байт первым |
| `SW::SwCmdCoder::encodeInt(v)` | `Int_B16LE(v, 3)` — 6 hex-символов, «Revu24» |
| `SW::SwCmdCoder::encodeX32Int(v)` | `Int_B16LE(v, 4)` — 8 hex-символов, только для cmdX |
| `SW::SwCmdCoder::decodeInt` / `decodeX32Int` | обратные |

Проверка на известном: `extendedInquire(axis, 1)` → `Int_B16LE(1, 3)` → `"010000"`
→ команда `:q1010000\r`. Совпадает с тем, что мы шлём и что плата понимает.

Приложение умеет четыре транспорта, все сводятся к одному и тому же

#### Формат `G` (Set Motion Mode)

Из `d4b470`–`d4b4c4`, два ASCII-символа:

* символ 0 — по флагу «быстро/медленно» (`bool`-аргумент) и биту 8 режима:
  `true` → `'2'` либо `'0'`; `false` → `'1'` либо `'3'`;
* символ 1 — `'0'` или `'1'` по биту 0 режима, плюс `| 0x2`, если заданная
  скорость отрицательная (то есть бит направления).

Согласуется с packed-полями §5.2 спецификации.

### 5.3 Расширенные запросы `:q<канал><ID>` — приложение использует ровно два ID

| ID | Команда | Кто вызывает | Адрес |
|---|---|---|---|
| `000000` | `:q1000000` | `SwMountAxis::readAxisIndex` (legacy-ветка) | `d4abc4`, `w1 = wzr` |
| `010000` | `:q1010000` | `SwDevice::readStatusEx` | `bb8bdc`, `w1 = 1` |

Больше нигде `extendedInquire` не вызывается — **всего 2 места на всю программу**.

Это важное соответствие: спецификация (§5.7) знает ровно эти два ID, приложение
использует ровно эти два ID. Наши эксперименты (`RA_PROTOCOL.md` §6.2) нашли,
что на нашей плате отвечают ID `01`…`05`, а `00` отдаёт `!0` — то есть наша
плата **не поддерживает** индексатор исходного положения, зато имеет три
недокументированных ID (`02`, `03`, `04`, `05`), про которые приложение не знает.

| ID | Смысл | Кто вызывает | Адрес |
|---|---|---|---|
| `000000` | Start PEC training | `SwMCommand::setPpecTraining(true)` | `d6eacc` (`bic w1, w9, w1`) |
| `000001` | Cancel PEC training | `SwMCommand::setPpecTraining(false)` | там же |
| `000002` | Start PEC playback | `SwMCommand::setPpecPlayback(true)` | `d6eccc` (`cinc w1, w8, eq`) |
| `000003` | Cancel PEC playback | `SwMCommand::setPpecPlayback(false)` | там же |
| `000004` | Enable dual encoder | `SwMCommand::setEnableDualEncoder(true)` | `d6e32c` |
| `000005` | Disable dual encoder | `SwMCommand::setEnableDualEncoder(false)` | там же |
| `000008` | Reset axis indexer | `SwMountAxis::resetAxisIndex` | `d4adb8` |
| **`0D` + скорость** | **Set serial baud rate** | `SwDevice::setSerialBaudRate` | `bb9e6c`–`bb9ea4` |

ID `0x06`, `0x07`, `0x09` из спецификации приложение не использует.

#### `:W` ID `0x0D` — установка скорости UART, в спецификации отсутствует

Разбор `SwDevice::setSerialBaudRate(AXISID, unsigned baud)`:

```
bb9e6c  mov   w8, #0x851f
bb9e74  movk  w8, #0x51eb, lsl #16     ; магическая константа деления на 100
bb9e7c  umull x8, w2, w8
bb9e90  lsr   x8, x8, #32
bb9e94  lsr   w8, w8, #5               ; w8 = baud / 100
bb9e84  mov   w9, #0xd
bb9e98  bfi   w9, w8, #8, #24          ; id = 0x0D | ((baud/100) << 8)
bb9ea4  bl    SwCmd::extendedSetting
```

То есть ID расширенной настройки — **трёхбайтовое поле, где младший байт это
номер функции, а два старших байта — её аргумент**. Это ключ к структуре,
которую мы перебирали вслепую: в `RA_PROTOCOL.md` §6.2 мы гоняли средний и
старший байты `:q1` и получали `!0`; у `:q` (чтение) аргументов нет, а вот у
`:W` (запись) они есть и именно там осмысленны.

Пример для 115200: `115200/100 = 1152 = 0x480`, `id = 0x04800D`,
`Int_B16LE(id,3)` = `"0D8004"`, команда **`:W10D8004\r`**.

Спецификация в §5.9 обрывается на ID `000009`, про `0x0D` не знает. У нас в
проекте этой команды нет.

### 5.5 Семейство `:X` (cmdX) — целиком отсутствует в нашей спецификации

Формат из `SW::SwCmd::x(AXISID, unsigned char sub, CBytes data)` (`0xbba38c`):

```
:X<канал><2 hex номер подкоманды><данные>\r
```

Байт `'X'` пишется в `bba3e0`; `Int_B16LE(sub, 1)` даёт 2 hex-символа; затем
`CBytes::Append(data)`.

Две обёртки:

| Обёртка | Адрес | Что делает |
|---|---|---|
| `SwCmd::xRead(axis, id)` | `bba4e0` | `x(axis, 0x00, Int_B16BE(id, 1))` → `:X<ch>00<id>` |
| `SwCmd::xOperation(axis, id)` | `bba594` | `x(axis, 0x05, Int_B16BE(id, 1))` → `:X<ch>05<id>` |

#### Все подкоманды `:X`

| Подкоманда | Кто вызывает | Адрес | Назначение |
|---|---|---|---|
| `00` | `SwCmd::xRead` | `bba528` | чтение, следующий байт — ID величины |
| `01` | `SwMountAxis::setAxisPosition` | `d49b1c` | задать позицию оси (cmdX-вариант `E`) |
| `02` | `SwMountAxis::axisSlew_cmdX` | `d4a050` | движение с заданной скоростью (32-бит) |
| `03` | `CmdXUtil::initSpeedSecPerPeriod` | `d42968`, `d42adc` | движение/калибровка скорости (64-бит) |
| `04` | `SwMountAxis::axisSlewToSlew_cmdX` | `d4a5dc` | переход от одной скорости к другой |
| `05` | `SwCmd::xOperation` | `bba5dc` | операция, следующий байт — ID операции |
| `0A` | `SwMCommand::addTrailPointsOffset` | `d6f0c8` | сдвиг траектории trail points |
| `0B` | `SwMCommand::setMountClock_Raw` | `d6fe10` | установить часы монтировки |
| `0E` | `SwMCommand::sendAbsoluteTrailPoint` | `d6f63c` | загрузить точку траектории (время + координаты) |
| `0F` | `CmdXUtil::getAxisPosAndMountClock` | `d42e9c` | атомарно прочитать позиции обеих осей и часы |

#### ID чтения `:X<ch>00<id>`

| ID | Кто вызывает | Адрес | Что читает |
|---|---|---|---|
| `02` | `SwDevice::readStepsPerRev` | `bb83f0` | CPR (cmdX-аналог `:a`) |
| `03` | `SwMountAxis::updateAxisPosition_noStoreEvent` | `d49624` | позиция оси (аналог `:j`) |
| `06` | `CmdXUtil::readClockTicksPerSecond` | `d42d2c` | тиков часов монтировки в секунду |
| `0B` | `SwMountAxis::readAxisIndex` | `d4ab9c` | позиция индексатора оси (аналог `:q…000000`) |

#### ID операций `:X<ch>05<id>`

| ID | Кто вызывает | Адрес | Что делает |
|---|---|---|---|
| `00` | `SwMCommand::setShutterOpen(true)` | `d6e6ec` (`eor w1, w25, #1`) | открыть затвор |
| `01` | `SwMCommand::setShutterOpen(false)` | там же | закрыть затвор |
| `03` | `SwMCommand::clearTrailPoints` | `d6fcc4` | очистить очередь trail points |

#### Когда приложение использует cmdX

`SW::SwDevice::supportsCmdX()` по адресу **`0xbb8ecc`**:

```
bb8ee0  ldrh w8, [x0, #0x8c]     ; версия прошивки MC
bb8ee4  rev16 w8, w8             ; перестановка байт
bb8ee8  cmp  w8, #0x326
bb8eec  cset w0, hi              ; поддерживается, если версия > 0x0326
```

**Наша плата — `0x0311`, то есть `0x0311 <= 0x0326`, и cmdX она не
поддерживает.** Это ровно объясняет наблюдение из `RA_PROTOCOL.md` §7:
`:X1\r` → `!0` (Unknown Command). Приложение на нашей монтировке пошло бы по
legacy-ветке, которую мы и так реализуем.

Практический вывод: **семейство `:X` реализовывать в драйвере не нужно** — на
прошивке `0x0311` его нет. Но знать о нём полезно: если владелец обновит
контроллер или появится вторая монтировка, `:X<ch>0F` (позиции обеих осей плюс
часы одним запросом) заметно дешевле трёх раздельных запросов.

### 5.6 Команды спецификации, которые приложение НЕ использует

`S`, `T`, `U`, `L`, `B`, `Q`, `z`, `C`, `N`, `n`, `A`, `R`, `r`, `c`, `h`, `i`,
`k`, `m`, `D`, `d`.

Из этого стоит отметить:

* приложение **не читает** `:D` (период трекинга 1×) и `:c` (brake steps) —
  считает их само из CPR и частоты таймера;
* приложение **не использует** окна EEPROM (`:C`/`:N`/`:n`) и регистров
  (`:A`/`:R`/`:r`) вообще. Те самые окна, которые мы перебирали в §6.2
  `RA_PROTOCOL.md` в поисках напряжения, вендорское приложение не трогает;
* приложение использует **инкрементные** `H` и `M`, а не абсолютные `S` и `U`;
* `:L` (Instant Stop) не используется — всегда `:K`.

### 5.7 Скорость последовательного порта

`SW::SerialConnectableHelper::setupBaud` (`0xbb5f68`) перебирает:

| Значение | Кодировка в дизассемблере |
|---|---|
| **115200** | `mov w1, #0xc200` + `movk w1, #0x1, lsl #16` = `0x1C200` |
| **921600** | `mov w1, #0x1000` + `movk w1, #0xe, lsl #16` = `0xE1000` |
| **9600** | `mov w1, #0x2580` |

То есть приложение знает, что современные платы говорят на 115200 (наш случай,
`RA_PROTOCOL.md` §1) и умеют 921600, а 9600 из §6 спецификации — только
запасной вариант. Переключение делается командой `:W<ch>0D…` из §5.4.

## 6. Сверка с нашей спецификацией и нашими наблюдениями

### 6.1 Где сходится

| Утверждение | Наш источник | Подтверждение в APK |
|---|---|---|
| Кадр `:<cmd><ch><data>\r` | `RA_PROTOCOL.md` §1, спека §4.2 | `SwCmd::encode()` `0xbba648` |
| Терминатор только `\r`, `#` не используется | `RA_PROTOCOL.md` §6.1, §8 | во всём бинарнике нет ни одного места, где команда завершалась бы `#` |
| Канал `'1'`/`'2'` | спека §4.2 | `bba698`–`bba6ac` |
| Числа — LE-hex, верхний регистр | спека §4.5, `RA_PROTOCOL.md` §7 | `CBytes::Int_B16LE`, `.hex().upper()`-эквивалент |
| `:q…010000` = Status EX | `RA_PROTOCOL.md` §3 | `SwDevice::readStatusEx` `bb8bdc` |
| ID расширенных настроек 0–5, 8 | спека §5.9 | §5.4 выше, совпадает один-в-один |
| UDP, порт 11880, AP 192.168.4.1 | спека §7 | `UDPSwDeviceFactory::make` `bbe5ac`, `UDPConnectableHelper::bg_startConnect` `bbb7a8` |
| Напряжение с платы не читается | `RA_PROTOCOL.md` §6, §6.7 | §2 выше |

### 6.2 Где расходится

| Расхождение | Подробности |
|---|---|
| **Семейство `:X` (cmdX)** | Нет ни в спецификации, ни в `references/skywatcher.cpp`, ни у нас. Полностью восстановлено в §5.5 |
| **`:W` ID `0x0D` — скорость UART** | Нет в спецификации (§5.9 обрывается на `9`). Формат восстановлен в §5.4 |
| **Аргумент в старших байтах ID `:W`** | Спецификация подаёт ID как «шесть hex», не объясняя структуру. На деле младший байт — функция, старшие два — аргумент (`xxxx07` в §5.9 спецификации — тот же приём, но там он не обобщён) |
| **Скорости UART** | Спецификация §6 говорит только про 9600. Приложение начинает со 115200 и знает 921600 |
| **Наши ID `:q1{02..05}0000`** | Приложение про них **не знает**: `extendedInquire` вызывается ровно дважды, с ID `0` и `1`. Значит, это либо нечто отладочное в прошивке, либо специфика конкретной платы. Наш перебор здесь ушёл дальше вендорского приложения |
| **`:q1000000` (индексатор)** | Приложение его шлёт, наша плата отвечает `!0` — на `0x0311` индексатора исходного положения нет |
| **`min_period`** | Никакой таблицы `mount_code → min_period` в приложении **не найдено**. Значение `0x0600` из `src/skywatcher/motor.py` не имеет подтверждения и в APK (см. §9) |

## 7. Сетевой слой

### 7.1 Транспорт до монтировки

| Параметр | Значение | Где в коде |
|---|---|---|
| Протокол | UDP, без обёртки | `SW::UDPConverser`, `SW::UnixUDP` |
| Порт | **11880** | `UDPSwDeviceFactory::make`, `bbe5ac` (`mov w3, #0x2e68`) |
| Адрес точки доступа | `192.168.4.1` | `UDPConnectableHelper::bg_startConnect`, `bbb7a8` |
| Широковещательный адрес | `192.168.4.255` | там же, `bbb7bc` |

Одна команда — одна датаграмма, один ответ — одна датаграмма. Никакого
собственного бинарного протокола поверх нет: в UDP уходит тот же ASCII-кадр
`:<cmd><ch><data>\r`, который уходил бы в serial. Это прямо следует из
архитектуры: `SwConverser` собирает кадр через `SwCmd::encode()` и передаёт его
в `IConverserRaw`, а тот уже либо `UnixUDP`, либо `SerialPort`, либо BLE.

### 7.2 Обнаружение монтировки

`SW::QtUDPBroadcaster` рассылает пакеты широковещательно на порт 11880
(`broadcast`, `bc1258`), перебирая все локальные broadcast-адреса
(`SW::getLocalBroadcastAddrs`, `QtUDPBroadcaster::localIpList`). Есть также
`SW::BLESwConnectableHelper::deviceScanFinished` с тем же портом (`bd8cc4`) —
после BLE-сканирования.

Содержимое discovery-пакета я **не восстановил**: `CBytes` для рассылки
собирается динамически, строковых литералов там нет. Предполагаю (не проверено),
что это обычная короткая команда вроде `:e1\r`, поскольку отдельного формата
discovery в коде не видно, а `UDPConnectableHelper` сразу после рассылки
работает через тот же `UDPConverser`.

### 7.3 Настройка самого WiFi-модуля — AT-команды

Класс `SW::WMProgrammer`, транспорт — `atConversation(...)`. Это отдельный от
монтировки канал: команды идут не мотор-контроллеру, а модулю.

| Команда | Метод приложения | Адрес литерала | Назначение |
|---|---|---|---|
| `AT+CWMODE` | `getMode`, `getWMState`, `encode_setMode` | `b64668`, `b66654`, `b66be0` | режим WiFi (AP / STA / оба) |
| `AT+CWSAP` | `getAPSetting`, `encode_setAP_SSID_Pass_Chan_Sec` | `b64a68`, `b6717c` | параметры своей точки доступа |
| `AT+CWJAP` | `getSTASetting`, `encode_setSTA_SSID_Pass` | `b64fe8`, `b67d1c` | подключение к чужой сети |
| `AT+CWDHCP` | `getSTASetting`, `setSTA_EnableDHCP` | `b65308` | DHCP в режиме станции |
| `AT+CIPSTA` | `getSTAIP`, `getSTASetting`, `encode_setSTA_FixedIP` | `b66210`, `b6551c`, `b685ac` | IP в режиме станции |
| `AT+CIPAP` | `getAPIP` | `b65b30` | IP точки доступа |
| `AT+GMR` | *в коде не вызывается* | строка присутствует | версия прошивки модуля |
| `AT+CWMODE_CUR?` | *в коде не вызывается* | строка присутствует | текущий режим |

Планировщик записи настроек — `SW::WMProgrammerPlanner` (`readWifiSetting`,
`apply`, `writeWifiModeBoth`). Ни одна AT-команда не связана с питанием.

## 8. Как я перепроверял

Задание требовало второй независимый источник внутри самого APK. Что сделано:

1. **Формат кадра.** Восстановлен из `SwCmd::encode()`. Проверен обратной
   сверкой: `extendedInquire(axis, 1)` должен дать `:q1010000\r`, и именно эту
   команду мы шлём на живое железо и получаем `=008000\r`
   (`RA_PROTOCOL.md` §3). Сходится.
2. **Буквы команд.** Получены двумя независимыми проходами по дизассемблеру
   (по записи байта в структуру `SwCmd` и по вызовам фабрик). Оба прохода дали
   одинаковый набор. Дополнительно: каждая найденная буква имеет осмысленное имя
   вызывающей функции (`setStride` → `I`, `axisStop` → `K`), что само по себе
   вторая проверка.
3. **ID расширенных настроек.** Сверены с §5.9 спецификации: 0–5 и 8 совпадают
   дословно. `0x0D` не совпадает — и это заявлено как расхождение, а не как
   «спецификация неполна по недосмотру».
4. **cmdX.** Номера подкоманд получены из констант в регистре `w1` перед
   вызовом `SwCmd::x`. Проверка: имена вызывающих функций согласованы
   (`xRead` = подкоманда 0, `xOperation` = подкоманда 5 — обе константы
   сидят внутри самих обёрток, `bba528` и `bba5dc`). Отдельно проверил гейт
   `supportsCmdX()` и получил порог `> 0x326`, который **объясняет** уже
   снятое с железа наблюдение `:X1\r` → `!0` при версии `0x0311`. Это
   независимое подтверждение из другого источника.
5. **Отсутствие напряжения.** Пять независимых срезов: строки ASCII, строки
   UTF-16, таблица символов, содержимое экрана «Информация» из
   `GeneralInfoList::refresh()`, список команд ASCOM-совместимого API.
   Плюс проверка на ложные срабатывания: `Voltar` (португальский),
   `Battery Level` (таблица Qt Bluetooth), `adc` (QML-идентификатор),
   `n_power32.png` (иконка режима гибернации в справке, проверено по
   `assets/Help/ru/help-utility.html`).
6. **Сетевые константы.** Порт 11880 найден в трёх разных функциях
   (`UDPSwDeviceFactory::make`, `QtUDPBroadcaster::broadcast`,
   `BLESwConnectableHelper::deviceScanFinished`) и совпадает с §7
   спецификации.
7. **Справка приложения.** `assets/Help/en/*.html` прочитана на предмет
   упоминания индикатора питания — упоминаний нет; слово «power» встречается
   только в контексте «включить/выключить монтировку» и «Wi-Fi потребляет
   больше энергии».

## 9. Что осталось непонятным и почему

1. **Содержимое discovery-пакета по UDP.** `QtUDPBroadcaster::broadcast`
   принимает уже готовый `CBytes`, а собирается он в вызывающем коде без
   строковых литералов. Восстановить можно, но нужно проследить поток данных
   через несколько лямбд `std::function`; на статике это дорого. Предположение
   (не проверено): это обычная команда протокола, скорее всего `:e1\r`.

2. **Побайтовый формат полезной нагрузки cmdX.** Восстановлены номера
   подкоманд и назначение, но не раскладка полей внутри
   `CmdXUtil::cmdXEncodeAxisSpeed32/64`, `cmdXEncodeAxisPos`, `cmdXEncodeTime`,
   `cmdXDecodeBothAxisPos`. Для нашей задачи это неважно: прошивка `0x0311`
   cmdX не поддерживает (§5.5). Если понадобится — это отдельная работа по
   трассировке арифметики в четырёх функциях.

3. **Источник `min_period = 0x0600` для mount code `0x0A`.** В приложении
   ничего похожего на таблицу «код монтировки → минимальный период» нет.
   Вопрос из `RA_PROTOCOL.md` §2.2 остаётся открытым: число в
   `src/skywatcher/motor.py` по-прежнему без источника. Приложение вместо
   таблицы использует `SwDevice::speedFineAdjustmentPrecision_legacy`
   (`0xbb9abc`) — вычисляет достижимую точность скорости из CPR и частоты
   таймера. Разбирать эту функцию целиком я не стал: она большая и завязана на
   `fmt::format` для отладочной строки. **Это стоящий следующий шаг**, если
   захочется обосновать предел скорости числом, а не догадкой.

4. **Строгое отрицание.** §2 доказывает, что *приложение* не читает напряжение.
   Оно **не** доказывает, что в прошивке `0x0311` такого регистра нет вовсе.
   Строго говоря, остаётся возможность «регистр есть, но вендорское приложение
   им не пользуется». Учитывая, что наш собственный перебор
   (`RA_PROTOCOL.md` §6.2: 256 регистров, 32 адреса ОЗУ, все свободные буквы,
   все ID `:q`) тоже ничего не дал, я считаю эту возможность маловероятной, но
   это оценка, а не доказательство.
