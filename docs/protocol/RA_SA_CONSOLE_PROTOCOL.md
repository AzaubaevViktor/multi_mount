# Протокол приложения SAM Console (Star Adventurer) — статический разбор APK

Документ описывает, **что именно приложение Sky-Watcher SAM Console шлёт нашей
плате**. В отличие от SynScan Pro (`RA_APP_PROTOCOL.md`), это приложение написано
ровно под Star Adventurer, поэтому всё, что оно делает, наша прошивка обязана
понимать.

Всё получено **статическим** разбором: приложение не запускалось, APK не
устанавливался, железо в ходе этого разбора не трогалось.

Каждое утверждение сопровождается виртуальным адресом в
`lib/arm64-v8a/libQtSAMApp_arm64-v8a.so` и/или именем символа. Где вывод —
предположение, это сказано явно.

Крупные машинные выгрузки вынесены в `docs/protocol/sa_console/` и перечислены
в §14.

## 0. Краткий ответ на главный вопрос

> ## Напряжение читается. Это **окно `:C` / `:n`**, адреса `0x0004` (батарея) и `0x001C` (USB), 16 бит little-endian, **делить на 100 → вольты**.

Дословно, для батарейного напряжения:

```
-> :C10400\r        ; установить адрес окна = 0x0004
<- <ответ приложение не разбирает, только проверяет, что он начинается с '='>
-> :n1\r            ; прочитать байт
<- =5C\r            ; ровно 4 байта: '=', две hex-цифры, '\r'  -> младший байт
-> :C10500\r        ; установить адрес окна = 0x0005
<- ...
-> :n1\r
<- =02\r            ; старший байт

raw = 0x02 << 8 | 0x5C = 0x025C = 604
V   = 604 / 100.0 = 6.04 В
```

Автоинкремента адреса приложение не использует: `:C` переустанавливается перед
каждым `:n`.

Для USB-напряжения — то же самое с адресами `0x001C` и `0x001D`.

Приложение показывает `Math.max(usbVolt, batteryVolt)` (§2.6), поэтому увиденные
пользователем **6.04 В при мультиметре 6.08 В** — это одно из этих двух чисел,
почти наверняка `batteryVolt`.

**Независимое подтверждение из наших собственных данных.** `RA_PROTOCOL.md` §6.2
уже зафиксировал живой дамп этого окна: «ненулевые только 0x04=`5D`, 0x05=`02`,
0x1C, 0x1D». Подставляем в найденную формулу: `0x025D = 605 → 6.05 В`. Мы держали
готовый ответ в руках и не знали, как его прочитать. Подробности и сверка — §2 и §12.

## 2. Питание — разбор до провода

### 2.1 Цепочка вызовов

`SW::SAM::readPowerStatus()` (`0x1f9820`) — только обёртка: кладёт задачу в
`QThreadPool`. Тело лямбды —
`QtConcurrent::StoredFunctionCall<SW::SAM::readPowerStatus()::$_0>::runFunctor()`
(`0x1fb448`), которая под мьютексом вызывает виртуальный слот `+0x88` объекта
`[SAM+0x10]`. По vtable `SW::SAMSync` (`sa_console/vtables.txt`) `+0x88` — это
**`SW::SAMSync::readPowerStatus()`**, `0x202678`. Там вся работа.

### 2.2 `SAMSync::readPowerStatus()` — арифметика

```
202690  ldr  x0, [x20, #0x10]      ; IClock
2026a0  blr  ...                   ; -> x21 = unixMs()
2026a4  ldr  x8, [x20, #0x80]      ; EEPROMConverser
2026ac  mov  w1, #0x4              ; адрес 0x0004
2026b8  ldr  x9, [x9, #0x18]       ; vtable +0x18 = EEPROMConverser::readInt16
2026bc  blr  x9
...
2026d4  mov  w1, #0x1c             ; адрес 0x001C
2026e0  blr  x8                    ; readInt16(0x1C)
...
202714  lsr  x8, x22, #48          ; результат первого чтения: биты 48..63
202724  sxth w8, w8                ; знаковое 16-бит
202728  scvtf d0, w8
20272c  mov  x8, #0x4059000000000000   ; = 100.0
202740  fdiv d8, d0, d1            ; d8 = readInt16(0x04) / 100.0
202734  lsr  x8, x0, #48
20273c  sxth w8, w8
202744  scvtf d0, w8
202750  fdiv d9, d0, d1            ; d9 = readInt16(0x1C) / 100.0
202754  stp  d8, d9, [x20, #0xb0]  ; кэш
202768  stp  d8, d9, [x19, #0x10]  ; возврат
```

Константа `0x4059000000000000` — это IEEE-754 `100.0`. Деление ровно на сто,
никаких опорных напряжений АЦП и делителей: **плата отдаёт готовое значение
в сотых вольта**.

Что подтверждает, что `+0x80` — это именно `EEPROMConverser`: vtable
`SW::EEPROMConverser` (`0x2d1338`) имеет `+0x18 = readInt16(unsigned short)`,
а конструктор `SAMSync` последним аргументом принимает
`shared_ptr<SW::EEPROMConverser>` (символ `allocator<SW::SAMSync>::construct<...>`),
и все восемь `shared_ptr`-полей ложатся по 16 байт с `0x10`: `IClock@0x10`,
`IWaitable@0x20`, `ISAMTaskState@0x30`, `ISAMSettings@0x40`, `ISwConverser@0x50`,
`ISwDevice@0x60`, `SwMountAxis@0x70`, `EEPROMConverser@0x80`.

### 2.3 Имена полей — из Qt-метаобъекта

`SW::SAMPowerStatus::staticMetaObject` (`0x2ce5b0`), разобран парсером:

```
CLASS SW::SAMPowerStatus  (rev 11)
  properties:
    batteryVolt   double  Readable,Writable,Required
    usbVolt       double  Readable,Writable,Required
```

`SW::SAMPowerStatus::qt_static_metacall` (`0x1db414`) читает свойство 0 из
`[gadget+0x8]`, свойство 1 из `[gadget+0x10]`. В возвращаемой структуре
`readPowerStatus` первый double лежит по `+0x10`, второй по `+0x18` (заголовок
`CmdRet` 8 байт + `qint64` времени 8 байт). Значит:

| Свойство | Адрес окна | Тип |
|---|---|---|
| **`batteryVolt`** | `0x0004` | int16 LE / 100 |
| **`usbVolt`** | `0x001C` | int16 LE / 100 |

### 2.4 `EEPROMConverser` — что уходит в порт

Вопреки имени, это не EEPROM (см. §12), а **окно чтения/записи по адресу**.

`SW::EEPROMConverser::readInt8(unsigned short addr)` (`0x200a58`):

```
200a88  bl   CBytes::Int_B16LE(addr, 2)   ; 2 байта LE -> 4 hex-символа
200a94  mov  w8, #0x43                    ; 'C'
200a9c  str  wzr, [sp, #0x10]             ; axis = 0  -> канал '1'
200aa0  strb w8,  [sp, #0x14]             ; буква команды
200af0  blr  ...                          ; converse(:C1<addr>\r)
200b28  mov  w8, #0x6e                    ; 'n'
200b30  str  wzr, [sp, #0x10]             ; axis = 0, полезной нагрузки нет
200b50  blr  ...                          ; converse(:n1\r)
200b8c  cmp  x8, #0x4                     ; длина ответа ровно 4 байта
200ba8  bl   CBytes::Slice(1, 3)          ; символы [1..2]
200bb4  bl   CBytes::B16LE_Int(&out)      ; 2 hex -> байт
```

* `Int_B16LE(addr, 2)` — два байта адреса младшим вперёд, каждый двумя hex-символами
  в верхнем регистре. Адрес `0x0004` → `"0400"`, `0x001C` → `"1C00"`, `0x0188` → `"8801"`.
* Кадр собирает `SW::SwCmd::encode()` (`0x232980`): `':'`, буква, канал
  (`'1'` при `axis==0`, `'2'` иначе), данные, `'\r'` — тот же формат, что у нас.
* Длина ответа проверяется как **4**. `SW::SwConverser::converse(CBytes)`
  (`0x240758`) кладёт в `CmdRet.data` **весь кадр вместе с `'='` и `'\r'`**
  (`240914`–`240958`: копируется весь срез от найденного `'='` до конца).
  То есть 4 байта — это `= X X \r`. `Slice(begin,end)` (`0x2456d4`, размер
  `end-begin`; для «позиция+длина» в библиотеке есть отдельная `SliceLen`)
  вырезает символы 1 и 2 — ровно две hex-цифры.

`readIntN(addr, n)` (`0x200dc4`) вызывает `readInt8(addr + i)` для `i = 0..n-1`
(`200e38: add w1, w24, w20`) и собирает байты через `CBytes::BytesLE_Int()` —
**младший байт по младшему адресу**. `readInt16 = readIntN(addr, 2)`
(`200d40: mov w2, #0x2`), `readInt32 = readIntN(addr, 4)` (`200f60`).

Важно: адрес переустанавливается **на каждый байт**, автоинкремента приложение
не использует. Полная посылка для одного 16-битного чтения — четыре команды.

Запись (`writeInt8_internal`, `0x200f78`): `:C1<addr 4 hex LE>\r`, затем
`:N1<value 2 hex>\r` (`201058: mov w8, #0x4e` = `'N'`).

### 2.5 Проверка формулой

| Величина | Значение |
|---|---|
| Показание приложения (со слов пользователя) | 6.04 В |
| Обратный пересчёт: `6.04 × 100` | **604** = `0x025C` |
| Байты в окне: `[0x04]`, `[0x05]` | `5C`, `02` |
| Наш собственный живой дамп (`RA_PROTOCOL.md` §6.2) | `[0x04] = 5D`, `[0x05] = 02` |
| Тот же дамп по формуле: `0x025D = 605` | **6.05 В** |
| Мультиметр в момент показа 6.04 | 6.08 В |

Три независимых числа — 604 (обратный пересчёт из UI), 605 (наш дамп 0x04/0x05)
и 608 (мультиметр) — сходятся в пределах 0.7 %. Это разные моменты времени и
разные измерители, так что расхождение ожидаемо.

Значение 604/605 «в сотых вольта» — осмысленное целое: 4×AA даёт около 6 В,
и шкала 0.01 В даёт разрешение 10 мВ при диапазоне до 327.67 В в знаковом int16.

Отдельно: наш `RA_PROTOCOL.md` §6.3 фиксировал, что `0x1C`/`0x1D` меняются
синхронно с `:q1030000` ≈ `0x0201D3`. Младшие 16 бит `0x01D3 = 467 → 4.67 В` —
это и есть `usbVolt`. А эксперименты §6.5 (значения `0xA6`…`0xCF` в младшем
байте при `0x01` в старшем) в новой шкале дают `0x01A6…0x01CF = 422…463`, то есть
**4.22…4.63 В с просадкой 0.4 В под нагрузкой**. Так что величина из §6.5
всё-таки была напряжением — ошибочной была не находка, а её шкала: мы
калибровали **младший байт**, тогда как физическая величина — 16-битная.

> **Статус утверждений §2.** Доказано из кода: адреса, кадры, порядок байтов,
> деление на 100, имена свойств. Доказано сверкой с нашим железом: значение
> `0x025D` в окне. **Не доказано:** какое из двух чисел видел пользователь
> (приложение показывает максимум из двух, §2.6).

### 2.6 Что именно рисует UI

QML скомпилирован в `.so`, но его таблица строк осталась читаемой. По смещению
`0x110800`–`0x111c00` в UTF-16 подряд лежат идентификаторы одного QML-компонента:

```
… | lastPowerStatus | Math | max | usbVolt | batteryVolt | %1V | arg | toFixed |
get | readPowerStatus | then | show | Updated power level | …
```

То есть биндинг вида `Math.max(sam.lastPowerStatus.usbVolt,
sam.lastPowerStatus.batteryVolt)`, форматирование `"%1V".arg(v.toFixed(n))`,
а `Updated power level` — тост после `readPowerStatus().then(...)`. Слово «level»
в тосте вводит в заблуждение: величина — вольты.

Строки `batteryVolt` и `usbVolt` встречаются в библиотеке **ровно по два раза**:
один раз в `qt_meta_stringdata` (ASCII, `0x10df73`/`0x10df7f`) и один раз в
таблице строк QML (UTF-16, `0x111074`/`0x11105c`). Других потребителей нет.

## 3. Карта окна `:C` / `:n` — то, что приложение считает регистрами платы

Собрано автоматическим проходом по всем вызовам `EEPROMConverser::*` из методов
`SAMSync` (машинная выгрузка — `sa_console/eeprom_map_raw.txt`; ниже сведено
руками с разбором `readStatus`/`readParamSet`).

### 3.1 Статус и питание

| Адрес | Ширина | Направление | Смысл | Откуда |
|---|---|---|---|---|
| `0x0000` | int8 | R | **режим** (`SAMMode`: 0 Manual, 1 AP, 2 Reg, 3 Long, 4 ATL) | `readStatus` `0x2022c4`, `readParamSet` `0x202854` |
| `0x0004` | int16 | R | **`batteryVolt` × 100** | `readPowerStatus` `0x2026bc` |
| `0x0008` | int8 | R | `maxPosErrReached` (bool) | `readStatus` `0x202330` |
| `0x000C` | int8 | R | `trackingOutOfAccuracy` (bool) | `readStatus` `0x202364` |
| `0x0010` | int32 | R | `numberOfPictureTaken` | `readStatus` `0x20239c` |
| `0x0014` | int8 | R | `longExposureTimelapseStatus` | `readStatus` `0x2023dc` |
| `0x0018` | int8 | R | `longExposureTimelapseErr10ms` | `readStatus` `0x202410` |
| `0x001C` | int16 | R | **`usbVolt` × 100** | `readPowerStatus` `0x2026e0` |

Имена полей — из `SW::SAMStatus::staticMetaObject` (`0x2ce560`); порядок чтения
и раскладка по стеку в `readStatus` совпадают со структурой поле в поле.

**Важная оговорка про этот блок.** Чтения `0x08`, `0x0C`, `0x14`, `0x18`
защищены условием `ldrb w9, [x20, #0xc8]` (`0x202310`, `0x202344`, `0x2023c0`,
`0x2023f0`). Поле `SAMSync+0xC8` записывается **только один раз, нулём**, в
конструкторе (`0x1ffa30` и `0x1ffa68`, `strb wzr`); ни одного присваивания
ненулевого значения во всей библиотеке нет. То есть в сборке 2.6.4 приложение
**фактически читает из статуса только `0x0000` и `0x0010`**, а четыре остальных
адреса — выключенная ветка. Их назначение известно из имён свойств, но
подтверждения «плата действительно так отвечает» у нас нет.

### 3.3 Управляющие «регистры-кнопки»

Записываются значением `1` по адресу, который сам кодирует действие:

| Адрес | Действие | Откуда |
|---|---|---|
| `0x0060` | LED полярного искателя — **включить** | `writePolarSightLightOn(true)` `0x204380` |

### 4.1 Чего в этом приложении НЕТ, в отличие от SynScan Pro

`O` (затвор), `P` (скорость автогида), `V` (яркость LED полярного искателя),
`s` (период PEC). Всё это здесь делается **через окно `:C`/`:N`** (§3.3), а не
отдельными буквами. Класса `SwMCommand` в библиотеке нет вообще.

Обратно: SynScan Pro **не использует** `C`/`N`/`n` (см. `RA_APP_PROTOCOL.md`
§5.6), а SAM Console на них построен целиком. Это ключевое различие двух
приложений и объяснение, почему прошлый разбор напряжения ничего не нашёл.

### 4.2 Расширенные команды — все места вызова

`SwCmd::extendedInquire` и `extendedSetting` вызываются ровно в пяти местах:

|---|---|---|---|

| `:q<ch>010000` | `SwDevice::readStatusEx` | `23ada4` (`mov w1, #0x1`) | Status EX |

`SwCmdCoder::encodeInt(v)` = `Int_B16LE(v, 3)` («Revu24»).

## 5. Последовательность подключения — дословно

`SW::SAMSync::connect()` (`0x201ff8`), аннотированный листинг —
`sa_console/disasm_SAMSync.txt`:

| # | Вызов | Что уходит в порт |
|---|---|---|
| 1 | `SwDevice::initRead(true, LogicalMode(1))` `0x202030` | см. ниже — `:e1`, `:a1`, `:f1`, `:b1` |
| 2 | `SwMountAxis::initRead(true)` `0x202048` | **ничего**: только кэширует `ISwDevice::initialized()` и `supportsCmdX()` в поля `+0x101`/`+0x102` (`0x232fb4`–`0x232fe8`) |
| 3 | `SAMSync::readDeviceName()` `0x202060` | окно: `:C1<addr>` + `:n1` для адресов `0x0090`…`0x00AF` — **64 команды** |
| 4 | `SAMSync::readStatus()` `0x202098` | окно: `0x0000` (int8), `0x0010`…`0x0013` (int32) — 10 команд |
| 5 | `SAMSync::readPowerStatus()` `0x2020b4` | окно: `0x0004`, `0x0005`, `0x001C`, `0x001D` — 8 команд |
| 6 | `SAMSync::lastStatus()` `0x2020f4` (без трафика), и если режим ≠ 0 — `SAMSync::readParamSet()` `0x202118` | окно: `0x0000`, `0x0028`, `0x0024`, `0x0030`, `0x0034`, `0x0038`, … |
| 7 | `SwDevice::lastAxisStatus(AXIS1)` `0x202134` — **из кэша шага 1, без трафика**; если бит 48 поднят → `SwMountAxis::setAxisPosition(AXIS1, 0.0)` `0x20216c` и `SwDevice::setAxisInitialized(AXIS1)` `0x202184` | `:E1000000`, `:F1` |
| 8 | `EEPROMConverser::writeInt8(0x6C, 1)` `0x202150` | `:C16C00` + `:N101` — зажечь индикацию подключения |

Раскрытие шага 1, `SW::SwDevice::initRead(bool oneAxis, LogicalMode)` (`0x23a404`):

* аргумент `true` формирует список из **одной** оси (`23a44c: mov w0,#0x4`, один
  `int`, значение 0); при `false` было бы две (`23a464: mov w0,#0x8`, `{0,1}`).
  Приложение всегда зовёт с `true` — это одноосевая монтировка;
* для оси: если версия ещё не прочитана — `initReadMCVersion(axis)` (vt `+0x20`,
  `23a4a4`) → **`:e1`**; затем `readStepsPerRev(axis)` (`23a4b4`) → **`:a1`**;
  затем `updateAxisStatus(axis)` (vt `+0x60`, `23a4cc`) → **`:f1`**;
* после цикла — `readStepTimerHz()` (`23a4e8`) → **`:b1`**.

**`:q1010000` (Status EX) в `connect()` не отправляется.** Он читается лениво,
при первом обращении к `mountStaticAttr()` — то есть из `hasAxisIndex()`
(`0x23477c`). `:g1` (high speed ratio) и `:j1` (позиция) в подключении тоже нет:
`:g1` читается внутри `axisSlew_legacy` перед каждым стартом движения (`0x233f2c`),
`:j1` — внутри `axisSlewTo_legacy` (`0x234380`).

Итого весь `connect()` — **4 обычные команды и 84 команды окна** (при режиме
Manual, без `readParamSet`).

Расшифровка бита 48 в шаге 7: `SwDevice::updateAxisStatus` (`0x23b108`) разбирает
ответ `:f1` = `=ABC\r` (проверка длины 5, `23b1c8`) и собирает упакованное слово
(`23b1fc`–`23b248`); бит 48 — это `bic w10, #1, C` (`23b218`), то есть
**«ось НЕ инициализирована»**. Значит ветка `setAxisPosition(0) + setAxisInitialized`
выполняется именно при сброшенном флаге инициализации.

Два наблюдения, полезных нашему `connect()`:

* приложение **не** шлёт `:F1` безусловно. Оно читает `:f1` в составе `initRead`
  и инициализирует ось только если флаг сброшен. Это согласуется с §11
  `RA_PROTOCOL.md` (лишний `:E` — источник проблем);
* последним действием подключения плата получает **запись** в окно (`0x6C`).
  Это единственная запись во всём `connect()`.

## 6. GOTO — как это делает вендор

`SW::SwMountAxis::axisSlewTo_legacy(AXISID axis, double targetRad)` (`0x234344`).
Это ветка для прошивок без cmdX, то есть **наша** (§9).

| # | Шаг | Адрес | Что уходит |
|---|---|---|---|
| 1 | `axisCheckStopWait(axis)` | `234368` | см. ниже |
| 2 | `updateAxisPosition(axis)` | `234380` | `:j<ch>` → текущая позиция в рад |
| 3 | `SwDevice::radToStep(axis, fabs(target − current))` | `2343c4` | локально, шаги |
| 4 | `setMotionMode(axis, mode, **true**)` | `2343fc` | `:G<ch>XY` |
| 5 | `setRelativeSlewToAbsSteps(axis, steps)` | `234410` | `:H<ch><6 hex>` |
| 6 | `setRelativeSlewToBrakeSteps(axis, **3500**)` | `234424` (`mov w2, #0xdac`) | `:M<ch>AC0D00` |
| 7 | `startMotion(axis)` | `234448` (хвостовой переход) | `:J<ch>` |

Три вещи, которые стоит выписать отдельно.

**Точка торможения — константа 3500 шагов.** Не доля пути, не функция скорости:
литерал `0xDAC` прямо в коде. При CPR 12 492 146 это 3500/12492146 × 360° ≈ **0.101°**
(6.1 угловой минуты) до цели.

**Режим считается из расстояния, а не из скорости.** В `axisSlewTo_legacy`
(`2343e4`–`2343f8`) собирается двухбитное поле: бит 0 = «`target − current > 0`»
(направление), бит 8 = «`|target − current| > 0.046669541409417` рад»
(константа по `0xcad30`, это **2.674°**). Для сравнения, `SwAxisMotionMode::fromSpeedRps`
(`0x232f30`) для обычного слежения использует порог по **скорости**
`0.0093339082818834` рад/с (константа `0xcae58`, ровно 128× сидерической).

**Формат `:G` — совпадает со спецификацией.** `SwMountAxis::setMotionMode`
(`0x2350b0`):

```
2350f0  tst  x23, #0x100                 ; бит «быстро»
2350f4  mov  w8, #0x33 ('3')
2350f8  mov  w9, #0x31 ('1')
235100  mov  w10, #0x30 ('0')
235104  csel w8, w9, w8, eq               ; медленно ? '1' : '3'
235108  mov  w9, #0x32 ('2')
235110  csel w9, w9, w10, eq              ; медленно ? '2' : '0'
235114  tst  w22, #0x1                    ; аргумент bool «это GOTO»
23511c  csel w8, w9, w8, ne
235120  tst  x23, #0x1                    ; бит направления
235124  cinc w22, w10, eq                 ; '0' если +, '1' если −
...
23512c  blr  ...                          ; Location::latitudeRad()
235138  fcmp d0, #0.0
235140  orr  w8, w22, #0x2                ; широта < 0 -> бит 1 (южное полушарие)
```

то есть символ 0: GOTO+быстро → `'0'`, слежение+медленно → `'1'`,
GOTO+медленно → `'2'`, слежение+быстро → `'3'`; символ 1: бит 0 — направление,
бит 1 — поднимается при **отрицательной широте**. Объект по `SwMountAxis+0xB8` —
`ILocation` (vtable `SW::Location` `+0x78 = latitudeRad()`).

### 6.1 Как ждут остановки

`SwMountAxis::axisCheckStopWait(axis)` (`0x234f34`):

1. `updateAxisStatus(axis)` → `:f<ch>`;
2. если ось идёт — послать **`:K<ch>`** (`234fc4: mov w8, #0x4b`; и `cinc w8, w8, ne`
   по флагу `SwMountAxis+0x100` даёт `'L'` — но это поле в библиотеке нигде не
   устанавливается, так что фактически всегда `'K'`);
3. цикл: `sleep(100 мс)` (`235044: mov w1, #0x64`, вызов по `ITCCancellable`),
   снова `:f<ch>`, пока бит Running не сбросится;
4. при отмене — код возврата 3 (`Cancel`).

**Опрос прибытия — тот же `:f<ch>` с интервалом 100 мс.** Никакого чтения
позиции для детекции прибытия, никакого `:c` (brake steps) — только флаг Running.

### 6.2 Обычное слежение

`SwMountAxis::axisSlew_legacy(axis, rps)` (`0x233db4`):
если `rps == 0` → `:K<ch>` (`233e94: mov w9, #0x4b`) и всё;
иначе `axisCheckStopWait` → `setMotionMode(axis, fromSpeedRps(rps), **false**)` →
`readHighSpeedRatio` (`:g<ch>`) → `setStride` (`:I<ch>`) → `startMotion` (`:J<ch>`).

## 7. Знает ли приложение про предел скорости

**Таблицы «mount code → минимальный период» в приложении нет.** Ни 1103, ни 1536,
ни `0x600`, ни `0x44F` в коде работы с осью не встречаются (единственные вхождения
`#0x600 = 1536` — `1d3c1c`, `1d3e34`, `1d42f8` — это `operator new[](1536)` внутри
`QHashPrivate::Data<...>::rehash`, к протоколу отношения не имеет).

Пересчёт скорости в период — `SwDevice::rpsToStride_(rps, cpr, timerHz)`
(`0x23b898`) и `rpsToStride(axis, rps)` (`0x23b77c`):

```
stride = (2π / cpr) × (timerHz / rps)        ; rps в рад/с, константа 2π по 0xcadd0
```

**Никакого зажима, никакого `max()`, никакой нижней границы.** Единственная
проверка — `rps < 0` бросает исключение `rpsToStride: expected positive rps`
(строка по `0xcb94f`).

Собственный предел у приложения всё-таки есть, но другой:

```
SW::SAMSpeedLimitRps()   0x204df8:  ldr d0, [0xcad88]  ->  0.00363610260832152
```

Это **рад/с**, что равно ровно `1/1728` об/с = 0.208333… °/с = 750″/с ≈ 49.86×
сидерической. Используется в `TaskProfile_AP::calculate()` (`0x2090b4`) и
`TaskProfile_RegLong::calculate()` (`0x211cc8`), где сравнивается с расчётной
скоростью профиля и при превышении выдаёт строки `Invalid Speed` (`0xccd93`)
или `Speed too fast for frame period and exposure` (`0xcc70d`). Наружу отдаётся
через QML-слот `QSAMHelper::getSpeedLimitRps()` (метаобъект `0x2ce6e0`).

Для нашей платы `0.0036361 рад/с` соответствует периоду
`16e6 × 2π / 12492146 / 0.0036361 ≈ **2213**`, то есть **приложение само себя
ограничивает вдвое строже, чем плата** (плата зажимает на 1103 = 100×).

**Вывод: 1536 в нашем драйвере не имеет источника ни в спецификации, ни в
SynScan Pro, ни в SAM Console.** Три независимых источника проверены, ни один
такого числа не содержит.

## 8. Специфика Star Adventurer

### 8.1 Режимы

`SW::SAMMode_` (метаобъект `0x2ce720`, QML-имя `SAMMode`):

| Значение | Имя | Что это |
|---|---|---|
| 0 | `Manual` | ручное управление / обычное слежение |
| 1 | `AP` | Astro Photo |
| 2 | `Reg` | обычный таймлапс |
| 3 | `Long` | таймлапс с длинной выдержкой |
| 4 | `ATL` | Astro Time Lapse |

Классы расчёта — `SW::TaskProfile_AP`, `TaskProfile_RegLong`, `TaskProfile_ATL`
(158 функций, `sa_console/disasm_TaskProfile.txt`), плюс `SW::CParamsSolver`.
Вся эта математика **не отправляет команд** — она считает параметры, которые
потом одной пачкой записываются в окно (§3.2) методом
`SAMSync::programAutoMode_writeParams` (`0x2032bc`).

### 8.2 Как запускается и останавливается автономная задача

* **Стоп:** `programManualMode()` (`0x202eb0`) — `writeInt8(0x20, 0)`, то есть
  `:C12000\r` + `:N100\r`. Один байт.
* **Старт:** `programAutoMode(params)` (`0x203064`) — сначала
  `programAutoMode_writeParams` пишет весь блок `0x24`…`0x4C` + `0x1A0`, `0x1B8`,
  **последним** `writeInt8(0x20, <код режима>)` (`0x2035e8`); затем в цикле до
  семи раз читает `0x20` (`0x203088`, `0x2030e8`, `0x203128`, `0x20316c`,
  `0x2031b0`, `0x2031f4`, `0x203238`), ожидая, что плата подтвердит смену режима.

То есть **регистр `0x20` — это одновременно команда и подтверждение**, а
подтверждение получают опросом. Ретраев по семи чтениям — это и есть ожидание.

### 8.3 Ведение по Луне/Солнцу

Отдельных команд для лунной/солнечной скорости в протоколе **нет**. Есть класс
`SW::QAstroRate` (метаобъект `0x2d27b8`) и QML-компонент `Param_AstroRateX` —
множитель считается на телефоне и уходит обычным `:I` (или пишется в `0x24`).

### 8.4 Возможности, зависящие от модели

`SAMSync::isSAWifi()` (`0x204678`): `mountModelCode() & 0xFF == 0x0A`.
**У нас mount code `0x0A`, значит `isSAWifi() == true`.** Отсюда:

| Метод | Формула | Для нашей платы |
|---|---|---|
| `isSAWifi()` `0x204678` | `mountCode == 0x0A` | **true** |
| `hasPolarSightLight()` `0x2046a4` | `!isSAWifi()` | **false** |
| `hasAutoShutdown()` `0x2046c8` | `!isSAWifi()` | **false** |

То есть регистры `0x60`/`0x64` (LED искателя), `0x0188` и `0x0184`
(автовыключение) приложение на нашей модели **не трогает**. Это согласуется с
`RA_PROTOCOL.md` §5.1: в Status EX бит «polar scope LED» сброшен.

## 9. Версионные гейты — что нам доступно, что нет

Версия хранится как 32-битное поле, собранное `SwCmdCoder::parseMCVersion`
(`0x232c08`) из ответа `:e<ch>` = `=B0B1B2` (шесть hex, разбор big-endian):
`биты 0-7 = B0`, `биты 8-15 = B1`, `биты 16-23 = B2` (mount code),
`бит 24` = признак валидности. Хранится по `SwDevice+0x8C..0x8F`.

Для нашей платы: `supportsCmdX` берёт `ldrh [+0x8c]` и делает `rev16`, получая
**0x0311**; значит `B0 = 0x03`, `B1 = 0x11`, `B2 = 0x0A`.

| Гейт | Адрес | Условие | Наша плата (`0x0311`, код `0x0A`) |
|---|---|---|---|
| `SwDevice::supportsCmdX()` | `0x23b094` | `rev16(ver16) > 0x326` | `0x0311 ≤ 0x0326` → **НЕТ cmdX** |
| `SAMSync::hasDithering()` | `0x2046ec` | `major > 3` или (`major == 3` и `(ver & 0xFE00) > 0x900`) | `major = 3`, `ver & 0xFE00 = 0x1000 > 0x900` → **ДА** |
| `SAMSync::hasShutterIntervalInMs()` | `0x204730` | та же формула | **ДА** — интервалы в миллисекундах, регистр `0x30` делится на 1000 |
| `SwMountAxis::supportsAxisSlewToSlew()` | `0x235780` | поле `+0x102`, устанавливается в `initRead` | требует cmdX → **НЕТ** |
| `SwMountAxis::hasAxisIndex()` | `0x23477c` | бит 16 ответа `SwDevice::mountStaticAttr()` (Status EX) | у нас бит сброшен → **НЕТ** (совпадает с `RA_PROTOCOL.md` §4) |

Порог `> 0x326` для cmdX **совпадает с найденным в SynScan Pro** — тот же общий
код, независимое подтверждение.

## 11. Ошибки, таймауты, ретраи

### 11.1 Разбор ответа

`SW::SwConverser::converse(CBytes const&)` (`0x240758`):

1. ищет первый байт `'!'` (`0x21`) или `'='` (`0x3d`) — `2407ec`, `2407f4`;
   если не нашёл — `logAbnormalResp` и `CmdRetType = 4` (`Other`);
2. срез от этого байта; требует длину ≥ 2 и последний байт `'\r'` (`0x240900:
   cmp w9, #0xd`); иначе — `Other`;
3. `'='` → `Ok` (тип 0), данные = **весь кадр вместе с `=` и `\r`**;
   `'!'` → `Nak` (тип 1).

Обратите внимание: **приложение не разбирает цифру после `!`.** Любой код ошибки
платы схлопывается в один `Nak`. Наша таблица кодов из `RA_PROTOCOL.md` §7
подробнее, чем то, что умеет вендор.

### 11.2 Коды результата

`SW::CmdRetType_` (метаобъект `0x2d2850`, QML-имя `CmdRetType`):

| Значение | Имя | Строка UI (`CmdRetTypeString`, `0x231de8`) |
|---|---|---|
| 0 | `Ok` | `Successful` (`0xccc10`) |
| 1 | `Nak` | — |
| 2 | `Timeout` | — |
| 3 | `Cancel` | `Operation canceled` (`0xcbc57`) |
| 4 | `Other` | `Communication error` (`0xcce3e`) |

### 11.3 Таймауты и повторы

Из конструктора `SW::ConnectionSettings` (`0x1ceb58`), значения читаются из
KV-хранилища с этими значениями по умолчанию:

| Настройка | Умолчание | Где |
|---|---|---|
| `readTimeoutMs_other` | **200 мс** | `0x1cec20` → константа `0xcad68` = 200, `0x1cec48: str d0,[x19,#0xc8]`; читается в `readTimeoutMs_other()` `0x2362bc` |
| `maxRetryCount` | **2** | `0x1cec60` → константа `0xcad70` = 2, `0x1ced04: str d0,[x19,#0xf8]`; читается в `maxRetryCount()` `0x236458` |
| `maxUpgradeBaud` | **115200** | `0x1cedb0` → `0xcada8`; `0x1cedb8` |

Ключ хранения счётчика повторов — строка `cxn.resends` (`0xcca95`).

При отсутствии реакции на любую команду вся операция (`connect`, `readStatus`,
`programAutoMode`) обрывается на первом же ненулевом `CmdRetType` — во всех
разобранных методах `SAMSync` проверка идёт сразу после каждого `converse`
(например `0x2022c8`, `0x202864`, `0x202894`). Отдельной «детекции перезагрузки
платы» в приложении **нет**: состояние подключения — это конечный автомат
`SW::ConnectableState_` (`0x2d2bc0`: `NotShown`, `Searching`,
`SearchListPopulated`, `Connecting`, `Failed`, `Connected`, `Disconnecting`),
и при ошибке он просто уходит в `Failed`.

### 12.1 Где сходится

| Утверждение | Наш источник | Подтверждение в APK |

| Кадр `:<cmd><ch><data>\r`, канал `'1'`/`'2'` | §1 | `SwCmd::encode()` `0x232980` |
| Терминатор только `\r`, `#` не используется | §6.1, §8 | `#` не встречается ни в одном месте сборки кадра; ответ обязан кончаться `\r` (`0x240900`) |
| Числа — hex в верхнем регистре, младший байт первым | §7 | `CBytes::Int_B16LE` |

### 12.3 Что можно безопасно попробовать на нашей плате

Напоминание о принятых ограничениях: `:W`, `:R`, `:N` и бутлоадер `:Q155AA` мы
не шлём принципиально; прошивку не трогаем.

**Безопасно — только чтение, ничего не меняет:**

| # | Что | Команды | Ожидание |
|---|---|---|---|
| 1 | **Напряжение батареи** | `:C10400` `:n1` `:C10500` `:n1` | два байта; `LE/100` ≈ 6.0 В, должно падать под нагрузкой и совпадать с мультиметром |
| 2 | **Напряжение USB** | `:C11C00` `:n1` `:C11D00` `:n1` | `LE/100`; при питании от батарей ожидаемо близко к нулю или к 4.7 В при USB |
| 3 | Режим монтировки | `:C10000` `:n1` | ожидается `00` (Manual), пока не запускали автономных задач |
| 4 | Счётчик снятых кадров | `:C11000` `:n1` … `:C11300` `:n1` | int32 LE; ожидается 0 |
| 5 | Имя устройства | `:C19000` `:n1` ×32 (адреса `0x90`…`0xAF`) | ASCII-строка SSID/имени |
| 6 | Скорость задачи (stride) | `:C12400` … `:C12700` + `:n1` | int32 LE — период таймера; сравнить с `:D1` и с 1103 |
| 7 | Флаги статуса (выключенная ветка, §3.1) | `:C10800`/`:C10C00`/`:C11400`/`:C11800` + `:n1` | проверка гипотезы: реальны ли эти регистры на `0x0311` |
| 8 | Настройки WiFi (только чтение) | `:C18400`…`:C18C00` + `:n1` | таймаут, режим, тип защиты |

Пункты 1 и 2 — приоритетные: они проверяемы мультиметром и закрывают вопрос
окончательно. Пункт 7 интересен тем, что вендор эти адреса **не читает**, так что
это чистая проверка гипотезы, а не воспроизведение вендорского поведения.

**Условно безопасно — движение, но по вендорскому сценарию (§6):**

| # | Что | Комментарий |
|---|---|---|
| 9 | GOTO на короткое плечо по схеме `:f` → `:j` → `:G<ch>2<dir>` → `:H` → `:M<ch>AC0D00` → `:J`, ожидание по `:f` каждые 100 мс | это **дословный вендорский порядок**. Наш §14 называет GOTO единственным большим непроверенным местом; теперь есть эталон. Начинать с расстояния < 2.674°, чтобы режим был медленный (`'2'`) |
| 10 | Проверить, что `:M` вообще принимается | `:M1AC0D00` при стоящей оси; вендор шлёт его всегда |

**Не пробовать (записи):** `:N1xx` в любой адрес окна — включая `0x20`
(запуск/останов автономного режима), `0x6C`/`0x70` (индикация) и весь блок
параметров. Регистр `0x20` меняет режим работы платы, а `0x60`…`0x70` —
физические выходы. Также не пробовать `:W10B0100`/`:W10C0100` (выключение WiFi —
может оборвать связь без возможности восстановить её тем же каналом).

## 13. Что осталось непонятным и почему

1. **Какое из двух напряжений видел пользователь.** UI показывает
   `Math.max(usbVolt, batteryVolt)` (§2.6). Статически различить нельзя; решается
   одним замером на железе (пункты 1–2 в §12.3).
2. **Физический смысл адресов `0x2C`, `0x38`, `0x3C`, `0x40`, `0x44`, `0x48`,
   `0x4C`, `0x1A0`, `0x1B8`.** Известно, что это параметры автономной задачи и в
   каком порядке они пишутся (§3.2), но соответствие «адрес ↔ поле экрана» требует
   трассировки `TaskProfile_AP/RegLong/ATL::calculate()` и `CParamsSolver` — это
   158 + 19 функций плотной плавающей арифметики. Не сделано.
3. **Смысл флага `0x28`.** Читается как bool в `readParamSet`, пишется в
   `programAutoMode_writeParams`; в метаобъекте `SAMParamSet` соответствующего
   свойства нет.
4. **Поле `SAMSync+0xC8`.** Гейт четырёх статусных чтений; в сборке 2.6.4
   всегда 0. Похоже на выключенный feature-флаг, но никакого кода, который бы его
   включал, в библиотеке нет — то есть это либо задел, либо остаток. Утверждать,
   что регистры `0x08`/`0x0C`/`0x14`/`0x18` существуют на плате, на основании
   этого кода **нельзя**.
5. **Поле `SwMountAxis+0x100`** (выбор `:K` против `:L`). Читается в
   `axisCheckStopWait`, но нигде не устанавливается — фактически всегда `:K`.
   Возможно, задел под Instant Stop.
6. **Формат ответа на `:C` и `:N`.** Код проверяет только `CmdRetType == Ok`
   и содержимое не разбирает, так что из APK известно лишь, что ответ должен
   начинаться с `=` и кончаться `\r`.
7. **Полезная нагрузка cmdX.** Не разбиралась: прошивка `0x0311` cmdX не
   поддерживает (§9), а класса-помощника `CmdXUtil` в этой библиотеке нет вовсе
   (в `SwMountAxis` есть только точки входа `axisSlew_cmdX`, `axisSlewToSlew_cmdX`).
8. **Логика `MountTaskManager` и `HandleController`** (10 и 30 функций) — это
   слой поверх `SAMSync`, команд сам не формирует. Выгружен
   (`sa_console/disasm_MountTaskManager.txt`, `disasm_HandleController.txt`),
   но не разбирался.
