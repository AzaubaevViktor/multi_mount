# Датчик ориентации и API для агентов

## Запуск и интерфейс

```sh
python -m src --sim
```

Экран калибровки и HTTP API доступны на `http://127.0.0.1:8080/`.
Адрес и порт задаются `--api-host` и `--api-port`. LX200 продолжает работать
через существующий TCP-сервер.

DEC передаёт только сырые векторы и состояние устройства. Все точки, их количество,
усреднение, перевод в Alt/Az и RA/DEC, сохранение и проверка расхождения находятся
в Python. Реальная прошивка сейчас отвечает `device_not_found`: модель, проводка
и драйвер физического датчика будут добавлены отдельно.

Симулятор по умолчанию предоставляет отдельный датчик. Его положение задаётся
в форме или API. SYNC меняет логические координаты монтировки и не меняет
сырые показания симулятора. Движение моторов пока также не меняет позу этого
датчика: для каждой сценарной точки нужно задать её отдельно.

Внизу экрана две каркасные схемы одной оптической оси: AZ/ALT относительно
горизонта и RA/DEC относительно экватора. Полярная ось учитывает широту места;
ориентация экваториальной сетки учитывает время измерения. Дуги показывают
углы и знак изменения, стрелки у конца трубы — компоненты скорости направления.
Положение также разложено на два цветных вектора: AZ/RA — проекция оптической
оси на горизонт/экватор, ALT/DEC — перпендикулярная составляющая от конца
проекции до конца оптической оси. Их сумма даёт единичный вектор LOS. Эти стрелки
показываются и при нулевой скорости; подписи содержат соответствующие углы.
Длины стрелок скорости усилены и нормированы к наибольшему вектору на обеих схемах;
численные скорости указаны отдельно в угловых секундах/с (для RA тоже угловых,
не секундах времени).

Скорости оцениваются в браузере по двум соседним пригодным показаниям датчика,
а не по командам моторов. У неподвижной трубы AZ/ALT не меняются, но RA меняется
с местным звёздным временем. Начальный отсчёт, изменение калибровки, повторный
sequence, разрыв более 5 секунд, ошибка связи и отсутствие координат скрывают
оценку скорости; переходы через 360° и 24h учитываются. У зенита/надира скорость
AZ не определена, у небесных полюсов не определена скорость RA. Скорости — средние
за интервал опроса, а не мгновенные показания гироскопа. В симуляторе схемы следуют
форме позы датчика; движение моторов само по себе пока не меняет эту позу.

## Сценарий калибровки

1. Задать широту и долготу места наблюдения. Долгота на восток положительная.
   Неуказанное место не подменяется координатами `(0, 0)`.
2. Включить сбор точек. «Начать / продолжить» сохраняет уже собранные точки.
   После изменения крепления сначала сбросить старые точки.
3. При съёмке кадра получить сырое измерение. Зафиксировать его `measurement_id`
   и `timestamp`. Для длительной выдержки нужно выбрать репрезентативное измерение
   при неподвижном телескопе.
4. Передать plate solve этого кадра через `/v1/sync`, привязав его к измерению.
   Повторить в нескольких различных направлениях и добавить повторные измерения
   для усреднения шума. Один и тот же отсчёт дважды в количество точек не входит.
5. Закончить сбор. Следующие SYNC проверяют расхождение с сохранённой калибровкой
   и не переобучают её. Для проверки качества использовать новые кадры и направления.

Обычный LX200 `CM` использует текущее измерение и его время: предварительно
заданный target RA/DEC поступает в тот же сервис. Для solve старого кадра нужен
HTTP API с `measurement_id`. Последние 512 измерений хранятся в памяти; неизвестный
или вытесненный ID отклоняется. Явное время solve должно совпадать с временем
измерения в пределах 0.5 секунды, иметь часовой пояс и соответствовать кадру.

Без датчика обычный SYNC монтировки продолжает работать; ответ API сообщает
`mount_synced: true`, `sample_added: false` и причину отсутствия сенсорной точки.

## Модель и пределы

Вектор гравитации задан в системе датчика, направлен вниз и измерен в м/с².
Магнитный вектор задан в той же системе, в мкТл. Гравитация определяет вертикаль,
магнитное поле даёт второе направление. Сам по себе наклон не определяет азимут;
базовая геометрия описана в [NXP AN4248](https://www.nxp.com/docs/en/application-note/AN4248.pdf).

Каждый solve переводится в ENU (East, North, Up) по месту и времени. Из пары
сырых векторов и известного направления вычисляется вектор оптической оси
в системе датчика. В отличие от идеального компаса, он может различаться
по точкам: так локально учитываются искажения магнитного поля корпусом.

Для нового измерения выбираются до четырёх ближайших точек в пространстве
направлений сырых векторов. Расстояние — максимум углов между гравитацией
и между магнитными векторами. Векторы оптической оси усредняются с весами
`1 / (1 + расстояние²)`. Совпадающие направления в пределах 0.1° усредняются
вместе, что корректно работает и на границе азимута 0°/360°.

Это локальная эмпирическая коррекция, не полная физическая модель магнитного
поля. Радиус области по умолчанию 25° в пространстве сырых направлений —
эвристика, не гарантия точности в 25° участка неба. Вне этой области координаты
отсутствуют. При противоречивых точках (отношение длины среднего вектора к сумме
весов меньше 0.95) они также отсутствуют. Реальную точность нужно проверить
независимыми plate solve на установленном датчике.

Вне режима сбора расхождение с новым solve больше 2° устанавливает
`calibration_drift` и скрывает доверенные координаты. Последний solve и его
ошибка сохраняются отдельно от последней калибровочной точки. Проверить
калибровку вне её области нельзя: SYNC сообщает `cannot_validate`, ошибка —
`null`. Расхождение не вычисляется по моторным координатам, только по
независимому solve. Успешная проверка, новая калибровочная точка или сброс
снимают флаг расхождения.

Измерения старше 2000 мс не используются. Модуль гравитации должен быть
в пределах 5–15 м/с²; почти вертикальное магнитное поле не даёт устойчивого
азимута. Эти проверки отсеивают явные ошибки, но не обнаруживают все
возможные магнитные возмущения. Без магнитного вектора полный Alt/Az и RA/DEC
не возвращаются. При неподвижном датчике Alt/Az остаётся прежним, RA меняется
с местным звёздным временем. Используется существующая астрономическая
геометрия проекта без поправок на рефракцию; входные solve должны быть
в согласованной системе координат и эпохе.

## API v1

Все числовые значения конечные; boolean не принимается вместо числа.
RA задан в часах `[0,24)`, DEC и широта в градусах `[-90,90]`,
долгота на восток `[-180,180]`, азимут от севера к востоку `[0,360)`.

| Метод | Путь | Содержимое / действие |
|---|---|---|
| GET | `/v1/status` | Подключение монтировки, режим симуляции, сырые данные, калибровка и координаты |
| GET | `/v1/sensor` | Состояние датчика, ID и UTC-время измерения, sequence, age_ms, gravity_m_s2, magnetic_uT |
| GET | `/v1/calibration` | Режим, число точек, место, область, drift, последняя точка и последняя проверка |
| POST | `/v1/site` | `{"latitude_deg": ..., "longitude_deg": ...}`; смена места при наличии точек требует сброса |
| POST | `/v1/calibration/start` | `{}`; начать или продолжить накопление |
| POST | `/v1/calibration/stop` | `{}`; закончить накопление |
| POST | `/v1/calibration/reset` | `{}`; удалить точки и проверку, сохранить место |
| POST | `/v1/sync` | `{"ra_hours": ..., "dec_deg": ..., "measurement_id": "...", "timestamp": "..."}` |
| POST | `/v1/sim/sensor` | Только симулятор: поза либо сырые данные / неисправность |

У `/v1/sync` ID и время необязательны: без ID берётся текущий отсчёт,
без времени — время выбранного отсчёта. Ответ содержит `status`, `mount_synced`,
`sample_added`, `residual_deg`, координаты solve, ID и время. Ошибка в запросе —
HTTP 400; недоступное хранилище — 503; неизвестный маршрут — 404.
Отсутствие датчика — нормальный ответ 200 со статусом и `null` вместо данных.

`/v1/status.status` различает `not_connected`, `unsupported`, `device_not_found`,
`no_data`, `transport_error`, `invalid_data`, `stale_data`, `heading_unavailable`,
`uncalibrated`, `calibrating`, `ready`, `out_of_coverage`,
`calibration_inconsistent`, `calibration_drift`. Режим сбора хранится независимо
в `calibration.mode`, в том числе когда пригодных точек ещё нет.
Поле `calibration.revision` — счётчик изменений в текущем процессе, включая SYNC
и переключение режима сбора. Он позволяет сбросить оценку скорости после
изменения координатного решения; после перезапуска счётчик начинается заново.

Примеры управления симулятором:

```json
{"alt_deg": 45, "az_deg": 10, "mounting_deg": 17}
```

```json
{"state": "available", "gravity_m_s2": {"x": 0, "y": 0, "z": -9.807},
 "magnetic_uT": {"x": 0, "y": 20, "z": -40}, "age_ms": 2500, "frozen": true}
```

```json
{"state": "device_not_found"}
```

Магнитный вектор необязателен. Для отсутствующих данных используется `no_data`.
`frozen: true` прекращает обновление отсчётов; их возраст увеличивается.
Новая поза восстанавливает нормальные обновления. В реальном режиме маршрут
симуляции возвращает 404.

## Сохранение и границы модулей

По умолчанию файлы `state/sensor_calibration.json` и
`state/sensor_calibration_sim.json` разделены. Путь меняется флагом
`--sensor-calibration`. Эти локальные данные исключены из Git.
После каждой точки или проверки Python атомарно сохраняет JSON schema 1
с контрольной суммой SHA-256, местом, сырыми векторами, solve, временем,
последней проверкой и флагом расхождения. Режим накопления после перезапуска
выключен. Сброс сохраняет пустой профиль. Повреждённый файл не активируется:
`storage_error` сообщает причину, число точек равно нулю.

Сериализация, временный файл и fsync выполняются вне блокировки состояния.
Проверка поколения, атомарная замена файла и публикация профиля составляют
короткий commit. Подготовленный SYNC не может перезаписать одновременный сброс.
Сбой записи сохраняет предыдущий профиль и файл.

Чтение проходит через публичную возможность Motor, затем через AxisDEC под
существующей блокировкой транзакций мотора. TMC2209Motor использует обычный
обмен команд и общий codec, а не отдельный serial-канал. HTTP и LX200 вызывают
общий доменный SYNC. Смещение от датчика не подменяет GR/GD и управление
моторами: эти данные публикуются отдельно для наблюдения и проверки.

## Протокол DEC

Команда v2: `sensor`, ответ без подключённого драйвера: `1;sensor_flags=0;`.
В v3 opcode `0x30`, запрос пустой. Ответ — 19 байт в существующей рамке с CRC.
Сборка прошивки с этим контрактом сообщает в HELLO `protocol=3`, `firmware=3`.

| Смещение | Поле |
|---|---|
| 0 | flags u8: bit 0 device present, bit 1 gravity valid, bit 2 magnetic valid |
| 1–4 | sequence u32 |
| 5–6 | age_ms u16, насыщается до 65535 |
| 7–12 | gravity x/y/z i16, единица 0.001 м/с² |
| 13–18 | magnetic x/y/z i16, единица 0.01 мкТл |

Все многобайтные значения big-endian. Допустимы flags 0, 1, 3, 7.
Без соответствующих флагов зарезервированные нули не выдаются клиенту как
показания. Firmware и Python проверены общими фиксированными пакетами.
Старая прошивка с `unknown_cmd` распознаётся как `unsupported`.

## Проверки

`src/tests/units/test_pointing_sensor.py` покрывает обе версии serial-протокола,
отсутствующий датчик и старую прошивку, независимые позы, накопление и усреднение,
искажённое магнитное поле и произвольное крепление, новый контрольный solve,
область калибровки, отсутствующие/устаревшие/вырожденные векторы,
сохранение и перезапуск, повреждение файла, сбой записи и гонку SYNC со сбросом,
реальный HTTP-сервер и LX200 `CM`. Физическая точность, питание и подключение
датчика на телескопе ещё не проверены.
