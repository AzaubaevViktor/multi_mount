# Multi-Mount Architecture

## Назначение

Проект собирает гибридную монтировку из двух физических осей и публикует наружу один LX200-совместимый endpoint:

- RA управляется через SynScan/SkyWatcher backend;
- DEC управляется через самодельный контроллер на Arduino + TMC2209;
- клиент (`INDI`, `KStars`, `Ekos`) видит это как одну монтировку.

Текущая архитектура построена вокруг связки `LX200SimpleServer -> SkyLX200 -> Combiner -> AxisRA/AxisDEC -> Motor backends`.

## Верхнеуровневая схема

```text
LX200 client
  -> LX200SimpleServer
    -> LX200Handler.handle()
      -> SkyLX200
        -> Combiner
          -> AxisRA
            -> SkyWatcherMotor
              -> SerialLine
          -> AxisDEC
            -> TMC2209Motor
              -> SerialLine
          -> PolarCompensator
```

## Основные модули

### `src/__main__.py`

Точка сборки текущего runtime:

- ищет serial-устройства;
- создаёт `SkyWatcherMotor` и `TMC2209Motor`;
- оборачивает их в `AxisRA` и `AxisDEC`;
- соединяет оси через `Combiner`;
- создаёт `SkyLX200`;
- поднимает `LX200SimpleServer`.
- поднимает HTTP API и экран калибровки датчика; в `--sim` использует тот же
  граф объектов, который собирает `tools.sim_stack`.

### `src/pointing`

`PointingService` читает сырые векторы через публичный `AxisDEC.read_orientation_sensor()`
и возможность `Motor`, пользуясь существующим порядком serial-транзакций.
DEC не хранит калибровку и не вычисляет координаты. Python сохраняет точки,
место, последнюю проверку и флаг расхождения атомарно; вычисляет локальную
коррекцию, Alt/Az и RA/DEC. `SkyLX200.sync_from_solve()` объединяет SYNC из
LX200 и HTTP без изменения состояния target чужого LX200-клиента.
Моторные координаты и данные датчика остаются отдельными источниками.
Контракт и ограничения: [POINTING_SENSOR.md](docs/POINTING_SENSOR.md).

### `src/lx200/base_server.py`

`LX200SimpleServer` поднимает TCP-сервер и работает на уровне байтового протокола LX200:

- принимает поток команд `:<cmd>#`;
- отдельно обрабатывает alignment query (`0x06`);
- декодирует команду и передаёт её в `lx200.handle(...)`;
- сериализует ответ обратно в LX200-формат (`LX200SlewResult` для `MS` — отдельно
  от `0/1`-подтверждений);
- ловит `LX200BadCommandError` и любую другую ошибку команды: кривая команда
  клиента отвечается по протоколу и **не рвёт соединение**.

Сервер не знает ничего о конкретной механике RA/DEC. Монтировка одна, поэтому и
разговор один: пока клиент подключён, второй отвергается (`refused_clients`), а
каждое новое подключение начинается с `begin_client_session()` — чужие target
RA/DEC и manual-move не наследуются.

### `src/lx200/base.py`

Протокольный и доменный слой LX200.

Содержит:

- `LX200Commands`, `LX200SlewResult` (статус `:MS#`), `LX200BadCommandError`
  (кривой аргумент + чем на него ответить по протоколу);
- базовый контракт `LX200Base`;
- `LX200Handler`, который:
  - хранит target RA/DEC и site-координаты;
  - парсит LX200-команды: `parse()` и семейство `_parse_*`, отдельно от
    исполнения — кривой аргумент даёт `LX200BadCommandError`, а не голый
    `IndexError`/`ValueError` наружу;
  - маршрутизирует команды в доменные методы;
  - ведёт список активных manual-move направлений для `Qe/Qw/Qn/Qs`;
  - сбрасывает per-connection состояние в `begin_client_session()`.

Этот файл больше не содержит отдельного axis-specific handler слоя: общая логика оси живёт в `src/sky/axis.py`.

### `src/sky/lx200.py`

`SkyLX200` является адаптером между LX200-командами и двухосевой моделью `Combiner`.

Он:

- проксирует `connect()` / `stop()` в `Combiner`;
- читает и синхронизирует координаты;
- запускает `goto_to(...)`;
- переключает preset-скорости guide/center/find/max;
- маршрутизирует ручные движения и guide pulse-команды по направлениям.

### `src/sky/combiner.py`

`Combiner` связывает RA и DEC оси в одну логическую монтировку.

Ответственность:

- объединять `AxisRA` и `AxisDEC`;
- отдавать общую позицию `PointCoordinates`;
- запускать `goto_to`, `move`, `halt_*`, `set_sky_speed`;
- пересчитывать guide speed по длительности pulse;
- координировать `PolarCompensator`.

`PolarCompensator` в текущем коде не просто хранит смещение полюса, а использует повторяющиеся guide-команды как вход для оценки ошибки полярного выравнивания и затем возвращает corrective speeds обратно в `Combiner.set_sky_speed(...)`.

### `src/sky/axis.py`

Здесь живёт фактическое общее ядро RA/DEC.

`Axis`:

- хранит логическую позицию mount;
- хранит текущую целевую sky-speed;
- держит очередь `AxisCommand`;
- запускает фоновый `_motion_convertor` thread;
- переводит доменные команды (`change_speed`, `move`, `goto_to`, `halt_*`) в операции мотора;
- периодически компенсирует логическую координату по фактическому смещению мотора.

Есть две конкретные реализации:

- `AxisRA` поверх `Ha` / `HaPerSecond`;
- `AxisDEC` поверх `Dec` / `DecPerSecond`.

Текущая модель оси не оформлена как отдельная state machine таблица. Поведение строится вокруг:

- текущего `AxisMotionMode`;
- очереди команд;
- блокировки мотора;
- фоновой компенсации позиции при отсутствии новых команд.

### `src/skywatcher/` — драйвер RA, четыре слоя

Разделён на слои после того, как протокол был снят с живого железа: знание о
квирках платы перестало помещаться в один класс.

- **`codec.py`** — чистые функции, ни одного I/O: `Revu24`, сборка кадра
  `:<cmd><ch><data>\r`, разбор ответа `=` / `!`, разбор статуса;
- **`board.py`** — снимок возможностей, снятый при подключении: версия прошивки,
  mount code, CPR, частота таймера, highspeed ratio, Status EX и **собственный
  минимальный период платы**. Последний не угадывается по таблице констант, а
  измеряется: записать заведомо малый период, прочитать `:i1`, узнать, на чём
  плата зажала. Здесь же живёт `TimerPeriod` — период в отсчётах таймера платы:
  без арифметики, без `__index__`, без конверсий, потому что это сопряжённая
  величина к `StepsPerSecond` и путаница между ними уже стоила расхождения
  800× против 71.8×;
- **`session.py`** — состояние и квирки: строгая сериализация «запрос → ответ»,
  память о записанном (позиция, период, флаг инициализации), детекция
  перезагрузки платы, протокол работы с `:E`, ожидание фактической остановки,
  неидемпотентные команды;
- **`motor.py`** — то, что видит `Axis`. Тонкий, контракт прежний.

### `src/tmc2209/` — драйвер DEC

Python backend для самодельного контроллера на Arduino.

- **`protocol.py`** — кадр v3: `#` + длина + опкод + номер + payload + CRC16 и
  разбор с ресинхронизацией. Пришёл на смену построчному текстовому протоколу,
  который не имел ни длины, ни контрольной суммы, из-за чего потеря цифры
  *внутри* значения проходила все проверки;
- **`motor.py`** — автоопределение диалекта на `connect()` (плата обслуживает оба),
  сверка эха, команды движения, конвертация между шагами и `Dec`.

### `src/serial_wrapper/wrapper.py`

Общий serial transport:

- поиск устройства по шаблону;
- line-based запросы с timeout;
- reconnect/reset helper-методы для железа;
- `drain_after_error(logger, reason)` — слив линии после ошибки: **сначала
  прочитать остатки, потом сбросить буферы**. Порядок — свойство транспорта, а
  не протокола; обе копии в драйверах успели побывать неправильными, и вторая
  прожила с дефектом месяцы после починки первой.

### `src/clock.py`

Инжектируемый источник времени (`Clock`, `REAL_CLOCK`, маркер `NEVER`) и
`TtlCache[T]` — «значение + отметка времени + TTL», через который оба драйвера
читают медленно меняющиеся величины (напряжение, позицию). Кэш нарочно ничего не
решает: обновление, отступ после отказа и ответ при неизвестном значении —
политика, и она у драйверов разная.

### `src/sky/physics.py`

Доменные типы и арифметика:

- `Ha`, `Dec`, `AxisPos`;
- `HaPerSecond`, `DecPerSecond`, `Second`;
- `StepsPerSecond[SPEED_CLS]` и две конкретные оси — `HaStepsPerSecond`,
  `DecStepsPerSecond`;
- parsing / formatting / wrapping;
- инварианты для координат и скоростей.

Про шаговую скорость отдельно. Это самая аварийно-опасная величина в проекте, и
тип у неё нарочно устроен так, чтобы её нельзя было перепутать **ни с чем**:

| С чем можно было спутать | Почему нельзя теперь |
|---|---|
| период таймера платы | это `skywatcher.board.TimerPeriod`, другой класс без общей арифметики; мост между ними — только `SkyWatcherBoard.period_from_speed_sps` / `speed_sps_from_period`, которым нужны частота таймера и CPR |
| угловая скорость (`HaPerSecond`, `DecPerSecond`) | `StepsPerSecond` не наследует `AxisSpeed`: умножение на `Second` не определено. Перевод — только через геометрию оси, то есть через драйвер |
| скорость другой оси | параметр типа: `StepsPerSecond[HaPerSecond]` и `StepsPerSecond[DecPerSecond]` для mypy несовместимы. Нового параметра ни `Motor`, ни `Axis` не потребовалось — `SPEED_CLS` у них уже был |
| счётчик шагов (позиция, приращение, CPR) | те остались `int`, а скорость перестала им быть |

`MotorStatus[SPEED_CLS]` параметризован ровно ради поля `speed_sps`: статус —
единственное место, где шаговая скорость уезжает от своего драйвера в код,
который держит обе оси сразу (дашборд, `hw_session`, цикл оси).

### `telescope_dec/src/main.cpp`

Прошивка Arduino для DEC-контроллера:

- управляет TMC2209 через step/dir;
- **обслуживает оба диалекта сразу** — кадры v3 и прежний построчный текст,
  выбирая по первому символу строки. Дуальность нужна, чтобы перепрошитая плата
  оставалась совместимой с инструментами, которые ходят текстом;
- считает переполнение TX-кольца и **сообщает о нём явно** (`tx_overflow`);
  раньше кольцо на 255 байт обрезало ответ молча, без терминатора;
- экспортирует статус, конфигурацию и команды движения для `TMC2209Motor`.

Кодек кадра вынесен в `telescope_dec/include/frame_v3.h` без единого обращения
к Arduino — тот же файл компилируется под хост в
`telescope_dec/test/frame_v3_selftest.cpp` и проверяется теми же эталонными
кадрами, что и питон-тесты. Иначе две реализации CRC сошлись бы на одном и том
же неверном значении и были бы «согласованы» между собой.

## Поток команды LX200

### 1. Подключение клиента

1. `LX200SimpleServer.serve_forever()` запускает TCP listener.
2. Перед входом в accept loop сервер вызывает `sky_lx200.connect()`.
3. `SkyLX200.connect()` делегирует подключение в `Combiner.connect()`.
4. `Combiner.connect()` подключает обе оси и запускает поток полярной компенсации.

### 2. Обработка команды

1. Клиент отправляет `:<cmd>#`.
2. `LX200SimpleServer` выделяет команду из byte stream.
3. `LX200Handler.handle()` превращает первые символы в `LX200Commands`.
4. `LX200Handler._do_handle()` вызывает доменный метод.
5. `SkyLX200` проксирует вызов в `Combiner`, а тот уже в нужную ось или в обе оси сразу.
6. Ответ сериализуется назад в LX200-формат.

### 3. Координатные команды

- `Sr` / `Sd` только обновляют target RA/DEC внутри `LX200Handler`.
- `CM` вызывает `sync_telescope(...)` с сохранёнными target values.
- `MS` запускает `goto_to(...)` и отвечает `LX200SlewResult`: `0` — слю принято,
  `<код><причина>#` — нет. Коды 1/2 (под горизонтом / выше предела) зарезервированы,
  но не выдаются: для них нужна высота над горизонтом, а `Gt`/`GL` пока константы.

## Модель оси в текущем коде

Каждая ось хранит:

- логическую mount-позицию (`_ra_position` / `_dec_position`);
- последнюю известную позицию мотора;
- текущую sky-speed;
- очередь команд;
- текущий `AxisMotionMode`;
- служебное состояние для manual move и GOTO.

Движение оси состоит из двух переплетённых путей:

- command path:
  - публичные методы кладут `AxisCommand` в очередь;
  - `_motion_convertor` вычитывает команду и выполняет нужную моторную операцию;
- compensation path:
  - когда очередь пуста, `_motion_convertor` читает положение мотора;
  - сравнивает ожидаемое и фактическое смещение;
  - корректирует логическую mount-позицию.

Именно поэтому клиент видит не raw encoder state, а логическую координату после компенсации tracking / guide / halt.

## RA и DEC различаются по hardware semantics

### RA

- tracking по умолчанию построен вокруг sidereal speed;
- ручное движение east/west меняет скорость относительно tracking;
- SkyWatcher backend сам хранит часть motion state mount'а;
- goto выполняется через delta-based команды mount controller.

### DEC

- базовый tracking rate обычно `0`;
- speed является signed относительно north/south;
- backend напрямую управляет `direction`, `speed`, `acceleration`, `mode`, `run`;
- goto использует target mode контроллера.

## Параллелизм

В проекте несколько фоновых потоков:

- `LX200SimpleServer`: отдельный thread на клиента, но одновременно активен
  ровно один (остальные отвергаются);
- `AxisRA` и `AxisDEC`: по одному `_motion_convertor` thread на ось;
- `Combiner`: thread полярной компенсации.

Синхронизация строится в основном на:

- `threading.RLock` вокруг операций мотора;
- `queue.Queue` для команд оси;
- `threading.Event` внутри `Combiner` и `PolarCompensator`.

## Тестовое покрытие

По умолчанию `pytest` собирает **только** `src/tests/units` — быстрый слой без
железа. `src/tests/hw` требует подключённой монтировки и без неё падает на
*сборке*, поэтому в дефолтный прогон не входит намеренно и запускается явным
аргументом: `pytest src/tests/hw`.

Отдельно стоит `src/ra_conformance/` — набор протокольных кейсов, снятых
дословно с `docs/protocol/RA_PROTOCOL.md` и исполняемых **одним и тем же кодом**
против симулятора и против живой платы. Он существует, чтобы симулятор и железо
не могли разъехаться молча: небезопасные на железе кейсы отсекаются механически,
до записи в порт.

## Ограничения и текущие долги

- `Sh`/`So` сохраняются, но `MS` их не проверяет: нужна модель высоты над
  горизонтом (широта площадки + LST), а `GL`/`GC` пока константы.
- ACK-байт (`0x06`) не дренирует буфер: при `buffer_size > 1` ответ на alignment
  уходит раньше уже накопленной команды.
- Общий status contract для SkyWatcher и TMC2209 ещё не унифицирован.
- При переходе DEC через полюс RA пока не зеркалится на `+12h`.
- **RA не переживает прибытие в цель в режиме GOTO** — плата перезагружается,
  воспроизведено на живом железе. Обходной путь (тормозить своим `:K1`, не давая
  плате доехать) реализован в safe GOTO state machine `SkyWatcherMotor`.
- UART к TMC2209 восстановлен: запись микрошага проверяется чтением CHOPCONF,
  доступны диагностика драйвера и управление током. Статус сообщает защиту,
  активное разрешение шага и счётчик событий.
- **Обнаружение стопора опросом StallGuard через UART ненадёжно на стенде.**
  Следующий аппаратный шаг — DIAG → D2 и калибровка порогов; до его выполнения
  стендовый мотор остаётся выключенным. См. `telescope_dec/FIRMWARE_PLAN.md`.
- Веб-интерфейс удалён целиком; новый не спроектирован.
